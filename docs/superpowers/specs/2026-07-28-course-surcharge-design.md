# Спека: доплата к абонементу (`payments.kind='surcharge'`)

Дата: 2026-07-28.

**Цель:** дать возможность внести деньги, которые не покупают уроков, а добивают
цену уже купленного абонемента. Повод — реальный кейс: клиент оплатил полный курс,
из-за ошибки банка сумма пришла неполной, и теперь он ежемесячно доплачивает.

**Принцип:** доплата — это деньги без уроков, привязанные к конкретному абонементу
внутри оплаты. Она поднимает цену уроков ТОЛЬКО своего блока, не трогает баланс
уроков и не занимает лимит курса.

---

## 1. Проблема

Оплата в системе — неразрывная пара «деньги + уроки»: CHECK `payments_purchase_signs`
требует `lessons_count > 0`, а лимит курса не даёт продать больше уроков, чем в
программе направления. Поэтому доплату к цене уже купленного курса внести нечем:

- обычная покупка на 1000 ₽ упрётся в `cap_exceeded` — уроки курса выбраны;
- `kind='extra'` пройдёт мимо лимита, но добавит ученику уроки, которых он не
  покупал, и создаст партию с абсурдной ценой (1000 ₽ за 0.1 урока);
- не вносить вовсе — касса месяца занижена, себестоимость урока занижена.

## 2. Утверждённые решения (2026-07-28)

1. **Привязка — к абонементу, а не к оплате целиком.** Клиент мог купить весь курс
   одной оплатой; доплата идёт за конкретный блок.
2. **Дорожают только уроки своего блока** (4 урока), остальные сохраняют базовую цену.
3. **Пересчёт задним числом.** Отработанные деньги считаются из партий на лету, и
   подорожание меняет в том числе закрытые месяцы. Осознанно принято: цена урока
   абонемента должна быть единой для всех его уроков.
4. **Роль manager вносить доплату не может** — как и обычные оплаты (решение того
   же дня, `ReadStaffWriteAdmin` на `/api/admin/payments`).

## 3. Модель данных

Новый вид строки `payments`: `kind='surcharge'`.

| Поле | Значение для доплаты |
|---|---|
| `total_amount` | сумма доплаты, > 0 |
| `lessons_count` | NULL — уроков не несёт |
| `subscriptions_count` | NULL |
| `unit_price` | 0 |
| `parent_payment` (новое) | FK → `payments.id`, обязателен |
| `subscription_index` (новое) | номер абонемента внутри родителя, 1-based, обязателен |
| `direction` | копия направления родителя (для фильтров и отчётов) |
| `paid_at` | фактическая дата поступления денег |

CHECK-ограничения (миграция):

- `payments_kind_check` расширяется на `'surcharge'`;
- новый `payments_surcharge_shape`: для `kind='surcharge'` — `lessons_count IS NULL`,
  `total_amount > 0`, `parent_payment_id IS NOT NULL`, `subscription_index >= 1`;
- новый `payments_parent_only_surcharge`: у всех прочих видов `parent_payment_id IS NULL`
  и `subscription_index IS NULL`.

Существующие `payments_purchase_signs` / `payments_refund_signs` не трогаем: они
написаны через `~Q(kind__in=[...])` и на новый вид не распространяются.

`on_delete=CASCADE` (и Django, и db-level): доплата без своей оплаты бессмысленна.
См. [[project_alterfield_clobbers_db_cascade]] — db-каскад задаётся RunSQL и легко
теряется при последующих AlterField.

**Что в БД проверить нельзя:** `subscription_index` не должен превышать число
абонементов родителя — это зависит от другой строки. Валидация в сервисе (раздел 5).

`Payment` уже под `@pghistory.track` и в `apps/changelog/registry.py` — нужна
перегенерация триггеров миграцией и подписи новых полей в `apps/changelog/summary.py`.

## 4. Расчёт денег

### 4.1. Блоки

Блок = абонемент = **4 урока** (та же величина, что `LESSONS_PER_MONTH` в
`revenue_forecast.py`; вводим именованную константу и переиспользуем её). Оплата с
`lessons_count = 36` — это 9 блоков. Если уроков не кратно четырём (предоплата,
`kind='extra'`), последний блок неполный.

### 4.2. Дробление партий — только при наличии доплат

Оплата без доплат остаётся ОДНОЙ партией, как сейчас. Дробление включается только
для оплат, у которых есть хотя бы одна доплата:

```
партия блока k = { lessons: min(4, остаток), price_per_lesson: (base_k + surcharges_k) / lessons_k }
base_k = total_amount * lessons_k / lessons_count     (доля блока в сумме оплаты)
```

Порядок партий сохраняется: блоки идут подряд, на место исходной оплаты в очереди
FIFO. Для оплат без доплат расчёт остаётся байт-в-байт прежним — это главный
предохранитель против регрессии в существующих отчётах.

Пример: 44 000 ₽ / 9 абонементов / 36 уроков, доплата 1000 ₽ ко 2-му блоку.
Блоки 1 и 3–9 — по 1222.22 ₽ за урок; блок 2 — (4888.89 + 1000) / 4 = 1472.22 ₽.
Сумма по курсу: 45 000 ₽.

### 4.3. Единое место построения партий

Сейчас партии строятся ДВАЖДЫ и почти одинаково: `fifo_inputs` (все ученики, для
отчётов и дашборда) и `student_fifo_remaining` (один ученик, для возврата). Логику
дробления дублировать нельзя — вводим общую чистую функцию

`apps/finances/lots.py::build_lots(payment_rows, surcharges_by_parent) -> list[lot]`

и оба места переводим на неё. Это устраняет существующее дублирование, а не
добавляет новое.

### 4.4. Что меняется само

- **Баланс уроков** — не меняется: `SUM(lessons_count)` игнорирует NULL.
- **Итого оплачено** (`total_paid_amount`) — вырастет: это `SUM(total_amount)` по
  всем строкам ученика, доплата попадёт автоматически.
- **Поступления месяца** (`collect_monthly_report`) — фильтр
  `kind__in=['purchase','extra']` расширяется на `'surcharge'`, иначе доплата не
  попадёт в кассу месяца, ради чего всё и делается.
- **Возврат средств** — считает остаток из партий, поэтому вернёт деньги уже по
  новым ценам без правок.
- **Лимит курса** — `create_payment` проверяет cap только для `kind != 'extra'`;
  добавляется ветка: доплата идёт мимо cap и мимо проверки ёмкости направления.

## 5. API

`POST /api/admin/payments` с `kind='surcharge'`, полями `parent_payment_id`,
`subscription_index`, `total_amount`, `paid_at`, опционально `note`.

Валидация в сервисе (400 с понятным текстом):

- родитель существует и принадлежит ТОМУ ЖЕ ученику;
- родитель — `purchase` или `extra` (к возврату и к другой доплате нельзя);
- `1 <= subscription_index <= ceil(lessons_count родителя / 4)`;
- `total_amount > 0`.

RBAC — `ReadStaffWriteAdmin` (уже стоит): менеджер получает 403.

`DELETE /api/admin/payments/:id` доплаты — обычным путём, цена блока возвращается
к базовой.

## 6. Интерфейс

История платежей на карточке ученика (`StudentBalanceBlock`):

- строка оплаты раскрывается в список абонементов: номер, диапазон уроков, текущая
  цена урока с учётом доплат;
- у каждого абонемента — действие «Доплата» (диалог: сумма, дата, комментарий);
- доплаты показываются отдельными строками под своим абонементом, с суммой и датой;
- всё — только при `canWritePayments` (админ/суперадмин);
- диалог удаления оплаты, у которой есть доплаты, показывает их число и сумму.

Компоненты формы — только из `components/form/`, цвета/отступы — токены.

## 7. Тесты

Модель и API:
- доплата создаётся, баланс уроков не изменился, лимит курса не занят;
- `subscription_index` больше числа абонементов родителя → 400;
- родитель чужого ученика → 400; родитель-возврат → 400;
- менеджер → 403 (создание и удаление);
- удаление родителя уносит доплаты (каскад).

Деньги:
- цена уроков блока с доплатой выросла, остальных — нет;
- сумма по всем партиям = сумма оплаты + доплат (до копейки);
- оплата без доплат даёт РОВНО те же партии, что до фичи (регресс);
- половинные уроки (45 мин) — вес потребления не сбит;
- доплата попадает в поступления месяца по своей дате;
- возврат средств возвращает остаток по подорожавшим ценам.

Гейт: полный `pytest -q` (не по частям — см. [[project_test_db_django_db_setup_split]]),
typecheck admin SPA, браузерный смоук.

## 8. Риски

1. **Ретроспективный пересчёт.** Выручка закрытых месяцев меняется — это принятое
   решение, но пользователя оно может удивить при сверке со скачанными отчётами.
   В интерфейсе доплаты добавить предупреждение об этом.
2. **Дробление партий.** Ошибка в долях блока (`base_k`) искажает себестоимость.
   Защита: тест на равенство суммы партий сумме денег до копейки и правило «нет
   доплат — нет дробления».
3. **Два места построения партий.** Если перевести на общую функцию только одно,
   возврат и отчёты разъедутся. Оба перевода — в одной задаче.
4. **db-каскад.** Восстановить RunSQL после AlterField, иначе удаление оплаты
   упрётся в FK.
