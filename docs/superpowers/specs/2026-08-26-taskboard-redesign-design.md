# Переработка раздела «Задачи» — рабочее пространство вместо формы

Дата: 2026-08-26
Основание: ТЗ заказчика от 2026-08-26 (полный текст — в диалоге), решения приняты в брейншторме там же.
Предшественник: [`2026-08-24-taskboard-design.md`](2026-08-24-taskboard-design.md) — исходная спека раздела. Всё, что здесь не упомянуто, остаётся как там.

---

## 1. Задача

Раздел «Задачи» реализован и работает, но воспринимается как форма с параметрами задачи:
верх страницы занимает три горизонтальных ряда, карточка бедна, панель справа — длинный
список input'ов, а действия (сменить срок, посмотреть свои задачи, найти задачу по номеру)
требуют лишних шагов.

Цель — поведенческая, не косметическая: управлять задачами прямо из рабочего пространства.

Что уже есть и **не переделывается**: перетаскивание карточек на `@dnd-kit`, счётчики колонок
отдельным запросом, пагинация внутри колонки, недельный вид, лента активности, комментарии,
настройка воронок и стадий, блок задач на странице ученика.

---

## 2. Принятые решения

| Решение | Выбор | Почему |
|---|---|---|
| Объём | P0 + P1 из ТЗ, без вида «Список» | Цельный законченный кусок; «Список» — отдельная задача позже |
| Выбор воронки | Табы рядом с заголовком | Экономит ряд, воронка читается сразу |
| Перетаскивание в закрытую стадию | Закрывает сразу с результатом `done`, диалога нет | Сценарий ТЗ «перетащил — и всё»; поправимо через toast |
| Шапка колонки | Сплошная цветная плашка (по скриншоту заказчика) | **Сознательно перекрывает §7 и §28 ТЗ**, которые залитые шапки запрещали |
| Шапка колонки — где живёт | Общий компонент для «Задач» и «Продлений» | Прямое требование заказчика: «касается всего компонента стадий в системе» |

## 3. Бэкенд (`journal_django/apps/taskboard`)

Модели и миграции **не меняются**. Четыре точечные правки.

### 3.1. Умный поиск `q`

Сейчас: `title__icontains`. Становится:

- строка вида `#124` или `124` → поиск по `id` (точное совпадение);
- иначе OR по: `title`, `student__full_name`, `assignee__full_name`, `tags__label`.

OR с join'ом по M2M `tags` размножает строки, поэтому:

- выдача карточек получает `.distinct()`;
- агрегат счётчиков колонок — `Count(..., distinct=True)`.

Без этого счётчик в шапке колонки соврёт относительно списка под ней — а это ровно тот
инвариант, ради которого `_filters_q()` существует в одном экземпляре с параметром `prefix`.

### 3.2. Фильтр `due`

Новое значение фильтра, `today | week | overdue | none`:

- `today` — `due_date = сегодня по MSK`;
- `week` — `due_date` в текущей календарной неделе (пн–вс, MSK);
- `overdue` — `due_date < сегодня AND closed_at IS NULL` (дублирует существующий `overdue`, оставлен как значение единого селектора «Срок»);
- `none` — `due_date IS NULL`.

Добавляется в `TaskFilterSerializer` и в `_filters_q()` — то есть автоматически действует и
на карточки, и на счётчики.

Сегодняшняя дата берётся через `apps.core.utils.dates.msk_today` — как уже сделано для `overdue`.

### 3.3. История правок в ленте

`services.update_task()` сейчас пишет `TaskActivity` только при смене исполнителя.
Добавляются записи `kind='system'` для: `due_date`, `priority`, `task_type_id`, `student_id`,
`group_id`, `title`.

Формат: `meta = {'field': <имя поля>, 'from': <старое>, 'to': <новое>}`. Значения — id и даты,
**не готовый русский текст**: иначе переименование стадии или тега задним числом переврёт
историю. Человеческий текст собирает фронт из тех же справочников, что рисуют карточку.

### 3.4. `comments_count` в строке карточки

`repository._base_queryset()` получает аннотацию: число записей `task_activity` с
`kind='comment'`. Одна подзапросная агрегация на страницу карточек; частичный индекс
`task_activity_task_idx` уже есть. Нужно, чтобы значок комментариев на карточке не стоил
отдельного запроса на каждую карточку.

Поле добавляется в `_row()` и в тип `TaskRow` на фронте.

## 4. Общий компонент шапки стадии

Требование заказчика шире раздела: одинаковая шапка колонки во всех досках системы.

**`components/board/BoardColumnHead.tsx`** — новый общий компонент:

```
┌─────────────────────────────────┐
│ В работе                    3   │  ← сплошная заливка цветом стадии
├─────────────────────────────────┤
│ карточки…                       │
```

- название слева, счётчик справа, плюс слот `actions` под кнопки (лупа поиска в «Продлениях»,
  меню в «Задачах»);
- скругление только сверху, плашка во всю ширину колонки;
- **цвет**: `stage.color`, заданный суперадмином; если не задан — детерминированный тон из
  названия стадии через существующий `nameColor()` из `lib/direction-color.ts` (тот же приём,
  что у направлений и аватаров). Серая заглушка отвергнута: доска из восьми одинаковых серых
  плашек хуже текущего состояния;
- **контраст**: цвет подписи вычисляется из относительной яркости фона — тёмная заливка даёт
  белый текст, светлая — тёмный. Цвет стадии выбирает человек, и светло-жёлтый с белым текстом
  ломает AA-контраст, который недавно чинился по всей системе.

Классы (`.board-col-head*`) живут в `styles/components.css` — файле общих компонентов.
Класть их в `pages/tasks.css` нельзя: вторая копия в `renewals.css` неизбежно разъедется.

**Переезжают на компонент:** `pages/tasks/TaskColumn.tsx` и `pages/renewals/RenewalColumn.tsx`.
Верхняя цветная полоска в 3px (`border-top`) у обеих колонок убирается — её роль забирает плашка.
Специфика «Продлений» (бейдж «авто» у прогресс-стадий, свёрнутый поиск) остаётся в разделе и
передаётся через слот, а не переезжает в общий компонент.

## 5. Верх страницы: три ряда → два

```
Задачи   [Общая] [Продажи] [Поддержка]                       [+ Новая задача]
[Все][Мои][Сегодня][Просроченные]  Приоритет ▾ Теги ▾ Фильтры ▾ 🔍Поиск   [Доска|Неделя]
```

### 5.1. Табы воронок

Селектор «Воронка» из отдельного ряда становится табами в шапке. При числе воронок больше
шести лишние уходят в «Ещё ▾» — ряд не должен переноситься.

### 5.2. Кнопка «+ Новая задача»

Основной CTA страницы, справа в шапке. Открывает `TaskCreateModal` — полную форму
(воронка, заголовок, исполнитель, срок, приоритет, тип, ученик, группа, теги, описание).
Быстрое создание внутри колонки остаётся и никуда не переносится.

### 5.3. Сегменты

Сегменты **не заводят своего состояния**. Это ярлыки, которые пишут обычные ключи фильтра в URL:

| Сегмент | Что пишет |
|---|---|
| Мои | `assignee_id=<текущая учётка>` |
| Сегодня | `due=today` |
| Просроченные | `overdue=true` |
| Все | сбрасывает эти три ключа |

Подсветка активного сегмента **выводится** из текущих фильтров. Второй источник истины
(отдельный ключ `seg=`) неизбежно разъехался бы с popover'ом «Фильтры».

### 5.4. Popover «Фильтры»

`TaskFiltersPopover` — новый компонент. Внутри: стадия, срок (`due`), приоритет, тип,
только открытые. На кнопке — счётчик активных фильтров. В основной строке остаются только
приоритет, теги и поиск.

## 6. Карточка задачи

```
#124  Высокий                                    ⋮
Проверить ученика
Python · Абдульманов Амир
👤 Павлов Илья                  📅 28 авг · просрочено 2 дн.   💬 3
```

- показываем **только заполненное**: нет типа — нет строки типа, нет тегов — нет ряда тегов,
  нет комментариев — нет значка;
- просрочка: бордовая точка и текст «просрочено N дн.». Заливки всей карточки нет — это
  требование ТЗ §18 и оно остаётся в силе;
- быстрые действия (открыть, меню `⋮`) появляются на hover, а не висят постоянно;
- вертикальные отступы режутся примерно на 20% (ТЗ §27);
- проп `compact` убирает срок — для недельного вида, где дату уже несёт колонка.

## 7. Панель задачи: форма → карточка

Ключевой компонент — **`pages/tasks/InlineEdit.tsx`**: по умолчанию значение показано текстом
с карандашом на hover; по клику превращается в нужный контрол из `components/form/`
(`DateInput`, `SelectInput`, `Combobox`), сохраняет по выбору или blur и схлопывается обратно.

Живёт в `pages/tasks/`, а не в `components/form/`: пользователь пока один, выносить в общие
компоненты преждевременно.

Структура панели:

1. **Шапка** — `#124`, заголовок, меню `⋮` (изменить, дублировать, перенести, удалить), `×`.
2. **Статус** — строка `● В работе` цветом стадии.
3. **КОНТЕКСТ** — исполнитель, ученик, группа. Значения текстом, правка через `InlineEdit`;
   ссылки «Открыть карточку →» остаются.
4. **СВОЙСТВА** — срок, приоритет, тип, теги.
5. **ОПИСАНИЕ** — если пусто, показывается строка «Добавить описание…», а не textarea на
   четыре строки; редактор раскрывается по клику.
6. **КОММЕНТАРИИ** — отдельный блок с формой ввода.
7. **ИСТОРИЯ** — timeline с точками.

Сегодня комментарии и системные события свалены в одну ленту «Активность» — они разделяются
по `kind`: `comment` идёт в блок 6, остальное в блок 7.

Автосохранение полей по факту изменения сохраняется — отдельной кнопки «Сохранить» в панели
нет и не появляется.

## 8. Toast и отмена

`components/ui/Toast.tsx` сейчас умеет только текст и жёстко живёт 3 секунды. Расширяется:

- необязательное действие `{ label, onClick }`;
- настраиваемое время жизни (для toast'а с отменой — дольше).

Отмена доступна там, где операция честно обратима:

| Действие | Отмена |
|---|---|
| Перенос между открытыми стадиями | Перенос обратно |
| Закрытие перетаскиванием | Возврат в исходную стадию — бэкенд сам обнулит `resolution` и `closed_at` |
| Создание, удаление | Нет |

Перетаскивание в закрытую стадию закрывает задачу сразу с результатом «Выполнено».
В toast'е — «Отменить» и «Изменить результат». Диалог выбора результата
(`TaskCompleteDialog`) остаётся живым для кнопки «Выполнено» в панели.

## 9. Недельный вид

- карточка идёт с `compact` — дата внутри неё не дублирует дату колонки;
- кнопка «Сегодня» видна всегда, а не только на чужой неделе;
- подсветка текущего дня — мягкий фон и акцентная дата вместо синей рамки, которую легко
  спутать с состоянием фокуса;
- плотность приводится к доске.

---

## 10. Быстрое добавление в колонке

Постоянно торчащее поле ввода вверху колонки заменяется на ссылку **+ Добавить задачу** внизу
колонки: по клику разворачивается в поле, Enter — создать, Esc — отменить (ТЗ §9 и скриншот
заказчика). Задача рождается в стадии своей колонки. В закрытых стадиях ссылки нет — бэкенд
запрещает создавать задачу сразу закрытой.

## 12. Проверка

- `pytest` из `journal_django/` — **полный прогон**, не по приложениям (часть приложений
  no-op'ит `django_db_setup`, прогон по частям даёт ложный результат);
- новые тесты бэкенда: поиск по `#id` / ученику / исполнителю / тегу и отсутствие дублей в
  выдаче и счётчиках; фильтр `due` во всех четырёх значениях; записи в ленту при смене срока,
  приоритета, типа, ученика, группы, заголовка; `comments_count`;
- сборка фронта — на типы;
- фронтенд-тестов в проекте нет, поэтому финал — ручной прогон заказчика в браузере:
  доска, неделя, панель задачи, «Продления» (общая шапка колонки затрагивает и их).
