# Дашборд «Финансы»: Revenue / Orders / Revenue daily·monthly

Дата: 2026-09-18. Страница `/admin/reports/dashboard/finance`.

## Что делаем

Плитка «Выручка за месяц» заменяется блоком в стиле внешней BI-панели:

- **Revenue** — сумма `payments.total_amount` за период: покупки, доплаты к
  абонементу и доп.уроки. **Возвраты (`kind='refund'`) исключены** (решение
  пользователя 2026-10-05; прежняя «Выручка за месяц» их вычитала). День, где
  был только возврат, показывает ноль, а не минус. Сами возвраты видны в
  «Отчётах» (реестр платежей — отдельная колонка) и в карточке ученика.
  Следствие: «Авансы» (Revenue − Recognized) на сумму возвратов завышены.
- **Orders** — количество оплат с `total_amount > 0` (возвраты не считаются заказом).
- **AOV** — средний чек = Revenue / Orders (Decimal на сервере, до копеек); нет
  заказов → `null` («—» на плитке). Плитка рядом с Orders и розовая линия на графике
  со своей шкалой от нуля (видна, когда AOV выбран один). На графике `null`
  рисуется НУЛЁМ: линия опускается, а не рвётся (решение пользователя 2026-09-30).
- **Revenue daily / Revenue monthly** — график с переключателем: зелёная кривая
  (daily) или столбики (monthly) — сумма, левая ось; синяя пунктирная линия —
  количество оплат, правая ось. Подсказка: «дата/месяц → Orders N, Revenue X ₽, AOV Y ₽».
  Дни/месяцы без оплат — нули (линия не рвётся).
  Подписи серий под графиком — кнопки-фильтры: клик оставляет только эту серию,
  повторный возвращает все; выбранный в одиночку AOV получает свою шкалу слева.
  Засечки подписей повторяют цвет и штрих линии, поэтому у легенды свои классы
  (`.revenue-legend__*`, объявлены ПОСЛЕ `.chart-legend__swatch`): общий класс
  жёстко красит засечку в акцент и перебил бы цвет серии.

- **Recognized revenue daily / monthly** (добавлено 2026-09-29) — отработанные
  деньги (FIFO) по дню урока и по месяцам периода, отдельный график тем же видом:
  линия по дням, столбики по месяцам, цвет бренда (не зелёный — чтобы не путался
  с поступлениями). Рядом плитка «Recognized revenue» = прежнее «Отработано за период».

- **Таблица «Курсы»** (добавлено 2026-10-07, по ТЗ пользователя со скриншотом BI-панели)
  — блок во всю ширину ПОД блоком Recognized revenue, последним на странице. Строка = направление оплаты, колонки:
  Purchases (число покупок, `kind='purchase'`), Months paid, Revenue (все
  поступления направления), ASP = Revenue / Purchases, ARPM.
  Решения пользователя:
  - **срок заказа в месяцах**: `subscriptions_count`, а где он не проставлен
    (поштучные покупки 1–3 уроков) — `lessons_count / 4`, то есть 1 урок = 0,25
    месяца. Доплата к абонементу (`surcharge`) своего срока не имеет: деньги
    идут в Revenue, в Purchases/Months/ARPM — нет;
  - **ARPM = среднее ПО ЗАКАЗАМ отношения «цена ÷ срок»**, НЕ Revenue / Months paid
    (на боевом примере пользователя это разные числа: 2807 против 2472);
  - **легаси-оплаты без направления** — отдельной строкой «Без направления»
    в конце, чтобы сумма столбца сходилась с плиткой Revenue.
  Сортировка по любому столбцу — на фронте (строк ≤ числа направлений), снизу
  строка «Итого»; средние в ней пересчитаны от итогов, а не усреднены по строкам.

Отложено по решению пользователя: Users, Courses.

## Период

Фильтр «Дата оплаты: от — до» (включительно) общий для всей страницы.
По умолчанию — последние 3 месяца по сегодня (МСК): `[сегодня − 3 мес; сегодня]`,
день месяца зажимается (31 → последний день короткого месяца). Дефолт считает
сервер (`services.default_period`) для обоих адресов (`/dashboard` и `/dashboard/revenue`),
поэтому «Отработано/Авансы» тоже считаются за 3 месяца, а Celery-прогрев default-ключа
сводки продолжает работать. Применённые границы приходят в ответе и показываются в
полях дат. «Сбросить» возвращает дефолт.

## API

`GET /api/admin/dashboard/revenue?from=YYYY-MM-DD&to=YYYY-MM-DD` — `IsManagerOrAdmin`.

- без обоих параметров — дефолт 3 месяца; без `from` — с первой оплаты в базе;
  без `to` — по сегодня (МСК);
- `invalid_date` (400) на кривую дату, `invalid_range` (400) при `from > to`.

Ответ: `{from, to, revenue, orders, aov, daily: [{date, revenue, orders, aov}],
monthly: [{month, revenue, orders, aov}], products: [{direction_id, direction,
purchases, months, revenue, asp, arpm}]}`.

`products` — ещё один GROUP BY по `direction_id` в том же запросе-периоде
(`repository.revenue_by_direction`): ARPM считает сама СУБД через `Avg` от
`total_amount / месяцы`, поэтому строки оплат в Python не выгружаются.

### Recognized revenue

Ряды едут в ответе `GET /api/admin/dashboard` (`recognized_daily`, `recognized_monthly`),
а не отдельным адресом: FIFO по всей базе — самый тяжёлый расчёт системы, второй
вызов удвоил бы его. Источник — новый разрез `worked_off_by_date` в `compute_fifo`
(пожизненный, точные Decimal; период режет сервис тем же предикатом, что и
`worked_off_month`).

При этом `worked_off_month` теперь считается как сумма точных дневных значений,
а не сумма покопеечно округлённых `worked_off_month` каждого ученика: иначе KPI
расходился с суммой ряда графика (на боевых данных — 2 копейки). Округление один
раз, как требует правило точности финансов.

Один GROUP BY по `paid_at` (индекс `payments_paid_at_idx` есть); месяцы и итоги
складываются в Python из дневных строк. Кэш — общий финансовый (генерация
сбрасывается сигналами Payment), TTL как у диапазонов.
