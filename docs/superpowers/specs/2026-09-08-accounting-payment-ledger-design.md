# Отчёт по поступлениям и выручке (реестр платежей)

Дата: 2026-09-08. Заказчик: пользователь (бухгалтерия KOTOKOD).
Отчёт до 2026-09-09 назывался «Бухгалтерский отчёт»; ключ типа остался
`accounting_month`, имя файла — `accounting_<месяц>.xlsx`.
Заменяет: `docs/superpowers/specs/2026-07-15-accounting-monthly-report-design.md`
(тип отчёта `accounting_month` тот же, содержимое листа переделывается целиком).

## 1. Задача

Сейчас «Бухгалтерский отчёт» — строка на ученика за месяц: посещено уроков,
отработано деньгами, блоки «Дата i / Платёж i» по оплатам месяца, остаток
оплаченных уроков, остаток аванса. Из него не видно **судьбу конкретного
платежа**: когда и сколько выручки он признал и сколько от него осталось
авансом.

Новый отчёт — реестр платежей: **строка = поступление клиента**, в строке дата
оплаты, цена 1 урока по этому платежу, признанная выручка по календарным
месяцам до выбранного включительно, выручка итого и остаток аванса.

Учётная природа та же, что у «Прогноза отработки денег»: признание выручки по
мере оказания услуг (ФСБУ 9/2020). Пока уроки не проведены — оплата это аванс
(отложенная выручка); урок переводит часть аванса в выручку. Новый отчёт —
фактическая сторона того же процесса (прогноз смотрит вперёд, этот — назад).

## 2. Решения пользователя (2026-09-08)

1. **Строка = платёж.** Ученик с пятью оплатами даёт пять строк подряд.
2. **Колонки-месяцы календарные**, общая шкала на весь лист (а не пары
   «Месяц i / Выручка i»): колонку месяца можно просуммировать.
3. **В отчёт попадают платежи, у которых есть признание выручки в выбранном
   месяце ИЛИ в этом месяце пришли деньги** (уточнено 2026-09-10; в первой
   редакции строку давало только признание). Оплата, внесённая в месяце, но ещё
   не начавшая отрабатываться, показывается с нулевой выручкой и полным авансом:
   касса месяца должна быть видна целиком.
4. **Аванс — на конец выбранного месяца**, не на сегодня. Отчёт за прошлый
   месяц воспроизводится одинаково, когда бы его ни собрали.
5. **Колонки строки:** ФИО, Platform ID, направление оплаты, дата оплаты, сумма
   платежа, доплаты отдельной колонкой, цена 1 урока, месяцы, выручка итого,
   возвращено, аванс.

## 3. Структура листа

Один лист «Реестр». Шапка и оформление — см. §4.6:

| # | Колонка | Содержимое |
|---|---------|-----------|
| 1 | ФИО ученика | `students.full_name` |
| 2 | Platform ID | `students.platform_id`, `-` если пусто |
| 3 | Направление оплаты | имя направления оплаты, `Без направления` если `direction_id IS NULL` |
| 4 | Дата оплаты | `payments.paid_at`, формат `ДД.ММ.ГГГГ` |
| 5 | Сумма платежа, ₽ | `payments.total_amount` (без доплат) |
| 6 | Доплаты, ₽ | Σ доплат (`kind='surcharge'`) к этому платежу; `0`, если их нет |
| 7 | Цена 1 урока, ₽ | `(сумма + доплаты) / lessons_count` |
| 8..N | `Месяц ГГГГ` | признанная выручка платежа в этом календарном месяце |
| N+1 | Выручка итого, ₽ | Σ колонок-месяцев |
| N+2 | Возвращено, ₽ | деньги платежа, погашенные возвратом (`kind='refund'`) |
| N+3 | Аванс, ₽ | неотработанный остаток платежа на конец выбранного месяца |

Сортировка строк: ФИО ученика → дата оплаты → id платежа.

**Шкала месяцев.** От самого раннего месяца, в котором хоть одна попавшая в
отчёт строка что-то признала, до выбранного месяца включительно — сплошь, без
пропусков. Месяцы позже выбранного не показываются и не считаются. Если строк
нет или ни одна из них ничего не признала — единственная колонка-месяц это сам
выбранный месяц.

**Сходимость строки (инвариант):**

```
Сумма платежа + Доплаты = Выручка итого + Возвращено + Аванс
```

## 4. Что считается и как

### 4.1 Источник — существующий FIFO, второй реализации не появляется

Партии (`apps/finances/lots.py::build_lots`) и очередь
(`apps/finances/fifo.py::compute_fifo`) остаются единственным местом правил.
Отчёту нужны два новых разреза тех же чисел — по платежу:

* `worked_off_by_month_payment: {(ГГГГ-ММ, payment_id): Decimal}` — признанная
  выручка партий платежа по месяцам. Симметричен существующему
  `worked_off_by_month_lot_direction`, накапливается в тех же местах.
* `remaining_by_payment: {payment_id: Decimal}` — непогашенный хвост в разрезе
  платежа (он же аванс). Симметричен `remaining_by_direction`.
* `refunded_by_payment: {payment_id: Decimal}` — деньги партий платежа,
  погашенные записями с флагом `refund` (возвраты уже приходят в `compute_fifo`
  синтетическими списаниями, сейчас они просто нигде не накапливаются).

Чтобы эти разрезы были возможны, `build_lots` кладёт в каждую партию
`payment_id` (он уже есть во входной строке — `r['id']`). Платёж с доплатами
даёт несколько партий с разными ценами, но с одним `payment_id`: в отчёте они
схлопываются в одну строку. Ключ опционален — партия без `payment_id` просто не
попадает в новые словари, поведение остальных потребителей не меняется.

### 4.2 As-of на конец выбранного месяца

Потребления (уроки, доп.уроки, сгорания, синтетические возвраты) обрезаются по
последнему дню выбранного месяца ДО вызова `compute_fifo`. Отсюда сразу и аванс
на конец месяца, и отсутствие месяцев позже выбранного — отдельной арифметики
не требуется.

Границы месяца — `apps.core.utils.dates.msk_month_range` (как в текущем
отчёте). `compute_fifo` вызывается с окном месяца
`[month_start, month_end_exclusive)`; `worked_off_month` отчёту не нужен, но
окно передавать обязательно.

### 4.3 Отбор строк

Платёж попадает в отчёт, если выполнено любое из двух:

* **признание**: `worked_off_by_month_payment[(выбранный месяц, payment_id)] > 0`;
* **приход денег**: `paid_at` внутри месяца, `kind` — `purchase` или `extra`.

Следствия, принятые сознательно:

* оплата месяца без проведённых уроков строку ДАЁТ: месяцы признания пустые,
  «Выручка итого» = 0, аванс = вся сумма с доплатами (решение 3);
* полностью отработанный в прошлом платёж в отчёт за текущий месяц не попадает;
* доплата к абонементу, пришедшая в месяце, втягивает в отчёт СВОЮ родительскую
  оплату — собственной строки у доплаты нет, а деньги пришли;
* возврат (`kind='refund'`) строки не создаёт: это не поступление, а отток; он
  виден колонкой «Возвращено» у платежей, чьи партии погасил;
* строка без единого месяца признания шкалу месяцев не двигает; если такими
  оказались все строки, шкала — сам выбранный месяц;
* «доплата за доп.урок сверх курса» (`kind='extra'`) — полноценная партия,
  поэтому даёт собственную строку. Колонка «Направление оплаты» берётся из
  самой оплаты (`payments.direction_id`), а не из партии: внутри FIFO партия
  `extra` намеренно идёт без направления (она не занимает лимит курса), но в
  реестре бухгалтерии важно видеть, за какой курс пришли деньги. `Без
  направления` показывается только когда у оплаты действительно нет
  `direction_id`;
* «доплата к абонементу» (`kind='surcharge'`) партий не образует и собственной
  строки не даёт никогда — её деньги видны в колонке «Доплаты» родительской
  строки и в её выручке/авансе.

### 4.4 Округление и невязка

Все промежуточные величины — точный `Decimal` (память
`feedback_financial_accounting_precision`). Округление до копеек один раз, на
выходе:

* каждая ячейка месяца округляется отдельно, а **невязка отдаётся последнему
  месяцу с признанием**, поэтому «Выручка итого» = Σ показанных месяцев точно
  (тот же приём, что в `apps/finances/revenue_forecast.py`);
* «Возвращено» округляется отдельно;
* **«Аванс» абсорбирует остаточную невязку строки**:
  `Аванс = (Сумма + Доплаты) − Выручка итого − Возвращено`.
  В точной арифметике это тождественно `remaining_by_payment` (каждый урок
  партии классифицируется либо в выручку, либо в возврат, а нетронутый хвост —
  это и есть остаток; Σ стоимостей партий платежа в точности равна
  `сумма + доплаты`, см. телескопическую сборку блоков в `build_lots`).
  Тест сверяет расхождение с `remaining_by_payment`: не больше 1 копейки.

### 4.5 Что в отчёт не попадает

Уроки, проведённые сверх оплаченных денег (`over_consumed_lessons`, «в долг»),
ни к какому платежу не привязаны. Поэтому сумма колонки месяца по всему листу
может быть меньше «отработано школой за месяц» ровно на величину такого долга.
Это осознанно: отчёт — реестр судьбы поступлений, а не отчёт о выручке школы.

### 4.6 Оформление листа

Стилистика по референсу заказчика (2026-09-08): шрифт Calibri 11 на всём листе,
шапка разбита на смысловые блоки, каждый со своим оттенком серого, текст шапки —
белый жирный, по центру, с переносом; высота шапки 32.

| Блок | Колонки | Цвет |
|---|---|---|
| Опорные (кто, за что и когда заплатил) | ФИО … Дата оплаты | `#595959` |
| Деньги платежа | Сумма, Доплаты, Цена 1 урока | `#7F7F7F` |
| Признание по месяцам | все колонки-месяцы | `#9C9C9C` |
| Итоги | Выручка итого, Возвращено, Аванс | `#595959` |

Данные: тонкая сетка `#D9D9D9`, дата по центру, деньги в формате `#,##0.00`.
Автофильтр на всю таблицу. `freeze_panes = 'E2'` — закреплена шапка ВМЕСТЕ с
четырьмя опорными колонками: месяцев бывает под полсотни, и при прокрутке вправо
строка иначе теряет имя ученика.

## 6. Производительность

Профиль тот же, что сейчас: один `fifo_inputs()` на всю школу, один
`compute_fifo` на ученика, запросов в цикле нет. Добавляются словари по
`payment_id` (порядка числа оплат) и один запрос метаданных платежей
(`id, student_id, paid_at, total_amount, direction__name, lessons_count`) по
отобранным id. Строк на листе — порядка числа платежей, признавших выручку в
одном месяце (сотни), а не всех оплат базы.
