# Переработка карточки преподавателя — дизайн

**Дата:** 2026-08-04
**Статус:** согласовано, к реализации
**Область:** admin SPA (`journal_django/frontend/admin-src`), `apps/teachers`

## Задача

Страница `/admin/teachers/:id` — самая бедная карточка сущности в админке.
Ученик и группа уже переехали на общий `EntityHero` + плитки показателей
(`docs/superpowers/specs` за 2026-07), преподаватель остался на дефолтном
заголовке `DetailShell`. Плюс три конкретных дефекта:

1. Выпадающий список Telegram визуально сломан — строки налезают друг на друга.
2. Блок Telegram висит между карточкой данных и списком групп без контейнера.
3. Группы (у активных преподавателей их 18+) идут одним плоским списком,
   активные вперемешку с архивными, каждая карточка несёт два факта на 90 px
   высоты.

И главное: по преподавателю **нет ни одного числа** — ни нагрузки, ни
направлений, ни размера групп.

## Решения (согласованы с пользователем)

| Вопрос | Решение |
|---|---|
| Норма вместимости группы | Не вводим. Поля `capacity` в БД нет и не будет — показываем фактический размер каждой группы и средний по преподавателю |
| Единица счёта нагрузки | **Занятий** (штуки) + **часов** (сумма `lesson_duration_minutes` ÷ 60). Вес half-lesson (0.5) здесь НЕ применяется |
| Замены | Считаются в общую нагрузку и в направление, но помечаются отдельной подписью «из них N замен» |
| Что учитываем | Только курсовые уроки: `lesson_type IN ('regular','substitution','reschedule')`. Доп.уроки (`extra`) и сгорания (`burned`) исключены |
| Период | Помесячно, переключатель ◀ ▶, открывается на текущем месяце (МСК) |

### Почему «часов», а не «академических часов»

45 / 60 / 90 минут не делятся на академчас (45 мин) ровно: 60 мин = 1,33 ач.
Дробное число в плитке породило бы спор о цифре. Берём астрономические часы,
а состав расшифровываем подписью: «90 мин ×34 · 60 мин ×5 · 45 мин ×8».

### Почему вес half-lesson не применяется к нагрузке

В финансах и прогрессе курса 45-минутное занятие = 0,5 урока — это мера
**программы**, а не труда. Преподаватель, отработавший 40 занятий по 45 минут,
провёл 40 встреч, а не 20. Смешение единиц уже давало баг (см.
`project_student_stats_halflesson_fix`), поэтому единицы здесь названы явно:
«занятий» — штуки, «часов» — время. Слово «уроков» на этой странице не
используется вообще.

## Архитектура

### Бэкенд: два эндпоинта в `apps/teachers`

Оба — `permission_classes = [IsManagerOrAdmin]`. Запись здесь не появляется,
`ReadStaffWriteSuperAdmin` не нужен.

```
GET /api/admin/teachers/<id>/stats?month=YYYY-MM
GET /api/admin/teachers/<id>/groups
```

`month` необязателен, дефолт — текущий месяц МСК. Невалидный формат → 400
`{"error": "..."}`. Несуществующий преподаватель → 404.

#### `/stats`

Три агрегата над `lessons ⨝ groups ⨝ directions`, фильтр по `teacher_id`,
диапазону дат месяца и `lesson_type IN COURSE_LESSON_TYPES`:

1. Итог месяца + разбивка по направлениям и по длительностям — один запрос
   с `GROUP BY direction_id, lesson_duration_minutes`, свёртка в Python
   (десятки строк, отдельные запросы не окупаются).
2. Счётчик замен — `COUNT(*) FILTER (WHERE original_teacher_id IS NOT NULL)`
   в том же запросе.
3. Помесячный ряд за последние 12 месяцев — отдельный `GROUP BY` по месяцу.
   Оттуда же берётся `last_lesson_date` (`MAX(lesson_date)` без ограничения
   месяцем — факт «когда вёл в последний раз» вне выбранного периода, он
   отвечает на вопрос «преподаватель ещё работает?»).

Контракт:

```json
{
  "month": "2026-07",
  "last_lesson_date": "2026-08-02",
  "total": { "sessions": 47, "minutes": 3750, "substitutions": 5 },
  "by_direction": [
    { "direction_id": 3, "name": "Minecraft", "color": "#f0b429",
      "sessions": 22, "minutes": 1980 }
  ],
  "by_duration": [ { "minutes": 90, "sessions": 34 } ],
  "monthly": [ { "month": "2025-09", "sessions": 38 } ]
}
```

**Ключ `sessions`, а не `lessons` — это не стиль, а защита от бага.**
В одном ответе живут две разные единицы: `sessions` — ЗАНЯТИЯ (штуки,
45-минутное = 1, нагрузка преподавателя), `lessons_done`/`lessons_total` в
`group_progress` — УРОКИ курса (с весом, 45-минутное = 0.5, прогресс
программы). Назвать обе «lessons» значило бы разложить те же грабли, на
которых уже подорвалась статистика ученика. Слово «lessons» в ответе
встречается только там, где вес применён.

`by_direction` сортируется по `sessions` убыв., при равенстве — по имени
(иначе порядок берётся из БД без `ORDER BY` и список прыгает между
одинаковыми запросами). `by_duration` — по `minutes` убыв., `monthly` — по
месяцу возр., ровно 12 элементов (месяцы без занятий присутствуют с нулём,
иначе спарклайн врёт о разрывах).

#### Группы преподавателя — БЕЗ нового эндпоинта

> **Уточнено при написании плана (2026-08-04).** Отдельный
> `GET /api/admin/teachers/<id>/groups` не нужен: существующий
> `GET /api/admin/groups` уже принимает `filter[teacher_id]` и
> `include_inactive=1` и уже отдаёт `members_count`, `direction_name`,
> `direction_color` и `slots` (`apps/groups/repository.py:178-197`,
> `apps/groups/views.py:68-80`). Не хватало только прогресса курса — он уехал
> в `/stats` полем `group_progress` (см. ниже). Описанный ниже запрос и
> ловушка двух `Count` относятся к `group_progress`.

Прогресс курса по группам преподавателя — в составе `/stats`:

```
Group.objects.filter(teacher_id=...)
  .annotate(students=Count('memberships', filter=Q(memberships__active=True)),
            lessons_done=Count('lessons', filter=Q(lessons__lesson_type__in=COURSE)),
            lessons_total=effective_total_lessons_expr())
```

Два `Count` по разным связям в одном запросе дают декартово произведение —
поэтому `students` и `lessons_done` считаются **двумя отдельными
подзапросами-агрегатами** (`Subquery(... .values('group').annotate(Count))`),
а не двумя `Count` в одном `annotate`. Это известная ловушка Django ORM и она
явно проверяется тестом.

Контракт строки в `group_progress`:

```json
{ "group_id": 102, "lessons_done": "18.0", "lessons_total": 36 }
```

`lessons_done` — в УРОКАХ курса (45 мин = 0.5). Приходит **строкой**: рендерер
проекта отдаёт `Decimal` через `str()`. Масштаб зафиксирован явным
`Cast(..., numeric(6,1))` — без него `SUM(CASE 0.5/1)` наследует масштаб
операндов и формат прыгает между `"2"` и `"1.5"` в зависимости от того, попало
ли в группу 45-минутное занятие.

`lessons_total` может быть `null` (длина курса не задана нигде) **или `0`**
(задана нулём в направлении — CHECK там допускает `>= 0`). Оба значения
означают «длины курса нет»: фронт прячет полосу прогресса. Делить без проверки
нельзя — получите `Infinity`.

N+1 запрещён: у активного преподавателя 18+ групп. Число запросов всего
эндпоинта фиксировано тестом (`django_assert_num_queries`) и не зависит от
числа групп и уроков.

Кеширование не вводим: два запроса на открытие карточки, а Redis-кеш дал бы
рассинхрон сразу после записи урока.

#### Combobox

Причина дефекта — `.combobox__item { height: 34px }` в `styles/forms.css:124`.
Длинная подпись переносится на вторую строку и вылезает за бокс. Правки:

- `height: 34px` → `min-height: 34px`, `align-items: flex-start`, `padding` по
  сетке 4 px.
- `Option` получает `hint?: string` — вторая строка, 12 px, `--text3`,
  моноширинная для `@ника`.
- `Option` получает `muted?: boolean` — занятые чужим преподавателем аккаунты
  приглушены и сортируются в конец списка, но **остаются выбираемыми**:
  перепривязка законна (человек сменил преподавателя), конфликт разрешает
  бэкенд. `disabled` заблокировал бы этот сценарий. *(Уточнено при написании
  плана: в первой редакции спеки здесь стояло `disabled?`.)*
- Поиск ищет по `label` **и** по `hint` (ник — то, что человек помнит).
- `ITEM_HEIGHT = 36` в `Combobox.tsx` — оценка высоты для `maxHeight`
  выпадашки. С двухстрочными пунктами становится 52; выносится в проп
  `itemHeight`, чтобы одностроч­ные выпадашки не потеряли компактность.

Занятая привязка перестаёт выглядеть как часть имени:

```
  Anna Dovidova
  @Anna_Dovidova · занят: Довыдова Анна
```

третью копию.

## Тесты

`pytest` из `journal_django/`, полный прогон (частичный даёт ложный результат,
см. `project_test_db_django_db_setup_split`).

- `/stats`: доп.урок и сгорание не попадают в счёт; замена считается и
  попадает в `substitutions`; `monthly` возвращает ровно 12 элементов с нулями;
  минуты суммируются по фактической длительности урока, а не группы;
  `last_lesson_date` НЕ ограничен выбранным месяцем; чужой преподаватель не
  виден; 400 на кривой `month`; 404 на несуществующего.
- `group_progress`: `lessons_done` не раздувается о число учеников группы
  (группа с 3 учениками и 2 уроками отдаёт 2, а не 6 — регрессия на ловушку
  двух `Count`); вес half-lesson применяется (три 45-мин занятия = 1.5 урока);
  `lessons_total` берётся из `groups.lessons_total`, если задан, иначе из
  направления, иначе `null`; архивные группы присутствуют; группа без уроков
  отдаёт 0, а не `null`.
- Производительность: число SQL-запросов фиксировано
  (`django_assert_num_queries` вокруг сервиса, а не вьюхи — иначе в замер
  попадут запросы аутентификации) и не растёт с числом групп и уроков.
- RBAC: `teacher` получает 403, аноним — 401.

Фронтенд-тестов в проекте нет; проверка — ручной прогон в браузере (обе темы,
узкий экран, преподаватель без групп и без Telegram).

VPS 2 CPU / 2 ГБ. На открытие карточки: 1 запрос преподавателя (есть сейчас) +

## Итерация 2 (2026-08-04, тем же днём)

### График — календарный год

Ряд занятий переведён со скользящего окна «12 месяцев назад от выбранного» на
**календарный год, январь–декабрь**. У скользящего окна при переключении месяца
◀ ▶ уезжали обе оси сразу — и данные, и подписи, — поэтому сравнить «стало ли
больше» было нельзя: картинка менялась целиком на каждый клик. У года ось
неподвижна, переключение месяцев внутри года график не двигает вообще. Выбранный
месяц помечен пунктирной линией, иначе непонятно, к какой точке относятся плитки.

Отдельного переключателя года нет: шагая месяцами через январь, человек и так
попадает в соседний год, а второй переключатель рядом с первым только запутал бы.

### Добавленные метрики

| Метрика | Ключ | Период | Примечание |
|---|---|---|---|
| Посещаемость | `attendance` | месяц | Знаменатель без `unpaid_skip` (ученик не посещает слот по устройству курса, это не «отсутствие у преподавателя»). `is_free` остаётся: ученик был. `pct: null` — считать не из чего |
| Дни недели | `weekday_load` | месяц | По ФАКТУ `lesson_date`, не по шаблону расписания: шаблон не показывает переносы и замены. Вс=0, как в `DOW` |
| Незаполненные | `unfilled` | **сейчас** | Переиспользует `dashboard.fill_service` (там уже порог overdue по МСК, доп.уроки и подмена преподавателя) |
| Пропуски | `absences` | месяц по `created_at` + `pending_now` сейчас | Привязка через группу пропуска. `created_at`, а не `scheduled_date`: у сгоревшего отработка не назначалась, даты нет |
| Зарплата | `payroll` | месяц | **Только суперадмину.** Ключ отсутствует у остальных, а не приходит нулями: «0 ₽» читается как «не заплатили» |
| Продления | `renewals` | **всё время** | Все, кто когда-либо был в его группах. Доля не эксклюзивна — см. раздел ниже |

`unfilled` и `absences.pending_now` вынесены на карточке в отдельную полосу
«требует действия», а не в ряд плиток: это единственные числа, которые зовут
что-то сделать, и среди нейтральных «занятий»/«часов» они бы потерялись. Когда
делать нечего — полосы нет вовсе.

### Отклонено по состоянию данных

**Пунктуальность отчётов — не строим.** Разобрано на боевых данных:
в январе–июне 2026 штрафов за просрочку **ноль**, при этом у **100%** уроков
`submitted_at::date ≠ lesson_date`. Вся история залита импортом, и отметка
времени показывает момент заливки, а не когда преподаватель сдал отчёт. Считать
по `submitted_at` — нарисовать «все просрочили»; считать по `payroll.penalty` —
нарисовать «все идеальны» (штрафы появились только в июле, 2 случая из 135).
Метрика станет осмысленной, когда teacher SPA поработает несколько месяцев:
сейчас через него записано 6 уроков из 11 581.

Дополнительная ловушка на будущее: admin SPA передаёт в
`calculate_penalty(submit_date=lesson_date)` всегда — административная запись
задним числом не штрафуется намеренно. Значит «просрочка» обязана считаться по
`payroll.penalty`, а не по таймстампу, иначе цифра разойдётся с деньгами.

### Продления — построены по правилу владельца продукта

Правило задано явно: берём **всех учеников, кто когда-либо состоял в группах
этого преподавателя** (членство неактивное и группа архивная тоже считаются —
ушедший ученик часть истории, иначе показываем только выживших), и считаем по
ним статистику продлений. Параллельное обучение у нескольких преподавателей
допустимо: ученик попадёт в статистику каждого.

Это не компромисс, а единственный возможный вариант: `renewal_deal` привязана
к **ученику и циклу**, направления или группы в ней нет вовсе, так что
разделить сделку между преподавателями данные не позволяют. Доля **не
эксклюзивна**, и подпись под блоком в «Обзоре» это проговаривает — иначе её
прочтут как личную заслугу.

`pct` = won / (won + lost) по **закрытым** сделкам (`RenewalStage.kind`).
Открытые в знаменатель не идут: ученик, по которому решение ещё не принято,
не «не продлился» — он в работе; их число отдаётся отдельно (`open`). `pct`
= `null`, когда закрытых нет: 0% и «данных нет» на экране выглядят одинаково,
а значат противоположное.

Период — **всё время**, не месяц: закрытых сделок у одного преподавателя
единицы в месяц, помесячная доля скакала бы от 0 до 100 на одной сделке.
