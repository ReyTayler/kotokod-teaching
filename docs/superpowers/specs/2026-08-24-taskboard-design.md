# Раздел «Задачи» (`apps/taskboard`) — дизайн

**Дата:** 2026-08-24
**Статус:** бэкенд реализован (2026-08-25/26), 146 тестов зелёные; фронтенд — план
`docs/superpowers/plans/2026-08-26-taskboard-frontend.md`, не начат

## 1. Цель

Механизм заведения задач на сотрудников внутри журнала: настраиваемые воронки,
настраиваемые стадии, карточки с исполнителем и сроком. Задачи бывают двух родов
и живут в одном разделе:

- **про учеников** — «позвонить по продлению», «оформить документы»;
- **про внутреннюю работу школы** — «заказать канцелярию», «обновить прайс».

Существующий раздел «Продления» (`apps/renewals`) **не затрагивается**: это
доменная механика с движком авто-стадий по посещаемости, циклами абонементов и
деньгами. Общего у разделов — только визуальный паттерн доски.

## 2. Почему не берём готовое

Проверены три формы интеграции; вывод — pluggable-решения с нужной функцией нет.

**pip-пакет внутрь проекта:**

| Пакет | Вердикт |
|---|---|
| `DjangoCRM/django-crm` | standalone-проект, не reusable app; Django 6.0+/Py 3.12+ против наших 5.1.4/3.11; UI целиком на Django Admin; своя модель прав; **AGPL-3.0** — заражает кодовую базу |
| `MicroPyramid/Django-CRM` | отдельный проект, Django-версия в maintenance mode, разработка ушла в SvelteKit-репозиторий |
| `django-todo` 2.6.2 | честно pluggable, BSD-3, живой. Но: канбана нет, настраиваемых стадий нет (статус = булев тумблер), REST API нет — только Django-шаблоны и login-required вьюхи, несовместимые с нашим JWT-cookie + CSP + React SPA |
| `django-helpdesk` | по классификации Django Packages — Project, не App; статусы захардкожены (Open/Reopened/Resolved/Closed/Duplicate); свой UI; пачка сторонних зависимостей |
| `django-river` | единственный reusable app с runtime-настраиваемыми стадиями, BSD — но мёртв: 3.3.0 от января 2021, Django ≤ 3.1, Python ≤ 3.8 |
| `viewflow` / `viewflow.fsm` | живой, но стадии описываются в коде, а не заводятся админом; OSS-версия AGPL, Pro платная |
| `koalixcrm`, `basxconnect`, Django ERP Framework | проекты и платформы, не подключаемые приложения |

**Отдельный сервис по API:** реальный кандидат — **Vikunja** (единый Go-бинарник,
PostgreSQL, ставится нативно под systemd без Docker, REST API, канбан с
произвольными колонками). Отклонён по четырём причинам: вторая система учётных
записей вне нашего RBAC/2FA/`token_version`; второй интерфейс, куда менеджер
должен уходить из журнала; **невозможность связать задачу с `Student` и `Group`**
— то есть потеря главного смысла размещения задач внутри журнала; и всё равно
требуемый код провижининга и синхронизации, который не даёт ни одной фичи.

**Встраиваемый фронтенд-компонент:** доска уже написана в разделе продлений
(`RenewalBoard.tsx`, `RenewalColumn.tsx`, `renewals.css`) — переиспользуется.

## 3. Отраслевые паттерны, положенные в основу

- **Задача ≠ сделка.** В Salesforce задача — это Activity с полями «тема, срок,
  ответственный, статус, приоритет» и ссылками на объекты; стадий у неё нет.
  В amoCRM и HubSpot так же: воронки со стадиями применяются к сделкам и тикетам.
- **Настраиваемые стадии — паттерн тикета**, а не задачи (HubSpot Ticket
  pipelines, Jira workflow на тип issue). То, что нужно нам, — именно он.
- **У настраиваемой стадии всегда фиксированная категория.** Salesforce: у
  значения статуса есть служебный флаг `IsClosed`. Jira: каждый статус
  принадлежит одной из встроенных категорий (To Do / In Progress / Done).
  Название и порядок — кастомные, семантика — из перечня. Это же реализовано
  у нас в `RenewalStage.kind`.
- **Результат отдельно от стадии.** Jira `Resolution`, обязательный результат
  задачи в amoCRM. «В какой колонке карточка» и «почему её закрыли» — разные
  вопросы.
- **Гибрид Битрикс/WEEEK** (жёсткий признак выполненности поверх произвольной
  колонки) сознательно **не берём** — см. раздел 6.

## 4. Область работ

**Входит:** воронки, стадии с категорией, карточки задач, ручное создание,
привязка к ученику и группе, срок, приоритет, теги, тип, результат при закрытии,
лента комментариев, доска, вид «Неделя», блок задач на странице ученика,
настройка воронок и стадий.

**Не входит (осознанный отказ):**

| Отброшено | Причина |
|---|---|
| Автогенерация задач по событиям | Требует идемпотентности и дедупликации. Заложена точка расширения (раздел 12), реализация — отдельной работой |
| Задачи для преподавателей, раздел в teacher SPA | teacher SPA сейчас в переработке; без Telegram-доставки раздел будет мёртвым. Модель допускает любого `Account` — расширение не потребует миграции схемы |
| Подзадачи и чеклисты | Явный отказ заказчика |
| Файлы-вложения | Явный отказ заказчика |
| Наблюдатели и уведомления | Явный отказ заказчика. **Следствие:** человек узнаёт о задаче, только зайдя в админку |
| Кастомные поля на карточке | Явный отказ заказчика |
| Учёт времени (оценка, таймер) | Инструмент для почасовой продажи времени; школе не нужен |
| Связи между задачами | Паттерн разработки, для «позвонить Ивановым» связей не бывает |
| Приватность задачи | В админке 10–15 человек, все свои |
| Ручная сортировка карточек внутри колонки | Порядок — по сроку и дате создания |
| Перенос задачи между воронками | У воронок разные наборы стадий, осмысленного правила соответствия нет |

## 5. Модель данных

Приложение — **`apps/taskboard`**. Название не `tasks`: Celery автоматически
ищет модуль `tasks.py` в каждом приложении, `apps.tasks.tasks` — заявка на
путаницу.

### `TaskBoard` — воронка

`id`, `name`, `description` (nullable), `sort_order`, `is_archived`,
`created_at`. Архивная воронка не предлагается при создании задач, но её задачи
остаются доступными.

### `TaskStage` — стадия

`id`, `board` (FK, CASCADE), `label`, `color` (nullable), `sort_order`,
`category`.

`category` — `TextChoices`: `open` («Открыта») / `closed` («Закрыта»).
Стабильного машинного ключа, как `RenewalStage.key`, здесь нет: он в продлениях
существует ради авто-правил движка, а движка у нас нет.

Ограничения БД:

- `UniqueConstraint(board, label)`;
- `CheckConstraint` на `category in ('open', 'closed')`;
- `CheckConstraint` на формат цвета `^#[0-9a-fA-F]{6}$` (nullable допустим).

У воронки обязана быть минимум одна стадия каждой категории — проверяется в
сервисе при удалении стадии, не CHECK: условие межстрочное и в CHECK не
выражается.

### `Task` — карточка

| Поле | Тип | Примечание |
|---|---|---|
| `id` | BigAutoField | он же человекочитаемый номер `#20` в интерфейсе |
| `board` | FK → TaskBoard, RESTRICT | |
| `stage` | FK → TaskStage, RESTRICT | стадию с задачами удалить нельзя |
| `title` | Text | |
| `description` | Text, nullable | |
| `assignee` | FK → accounts.Account, SET NULL, nullable | исполнитель |
| `created_by` | FK → accounts.Account, SET NULL, nullable | постановщик |
| `student` | FK → students.Student, SET NULL, nullable | |
| `group` | FK → groups.Group, SET NULL, nullable | |
| `task_type` | FK → TaskType, SET NULL, nullable | справочник |
| `due_date` | Date, nullable | **дата без времени** |
| `priority` | CharField choices | `low` / `normal` / `high` |
| `resolution` | CharField choices, nullable | `done` / `cancelled` / `irrelevant`; заполнено ⇔ стадия закрытая |
| `stage_entered_at` | DateTime | |
| `closed_at` | DateTime, nullable | |
| `created_at`, `updated_at` | DateTime | |

Срок — **дата без времени**. Время тянет за собой часовые пояса, а «позвонить в
15:00» — это уже календарь, а не задачник.

Признак «просрочена» **не хранится**: выводится как `due_date < сегодня AND
closed_at IS NULL`. Тот же принцип, что у балансов учеников.

`SET NULL` на ученике и группе: при жёстком удалении сущности задача остаётся,
теряя контекст. `RESTRICT` здесь неуместен — иначе старая задача заблокирует
удаление группы.

### `TaskTag`

`id`, `label`, `color` (nullable). Справочник. Связь с задачей — стандартная
`ManyToManyField` через автогенерируемую таблицу.

Промежуточная таблица связи pghistory **не трекается** (автогенерируемая модель
не наша). Чтобы смена тегов не пропадала из истории, она пишется записью
`kind='system'` в `TaskActivity`.

### `TaskType`

`id`, `label`, `sort_order`. Справочник («Звонок», «Встреча», «Дело»).

### `TaskActivity` — лента карточки

`id`, `task` (FK, CASCADE), `kind` (`stage_change` / `assign` / `comment` /
`system`), `author` (FK → Account, SET NULL, nullable), `text` (nullable),
`meta` (`TolerantJSONField`, nullable), `created_at`.

`TolerantJSONField`, а не `JSONField`: `apps.core.apps` регистрирует
`register_default_jsonb`, и psycopg2 отдаёт уже готовый объект — обычное поле
падало бы на `json.loads`.

### Индексы

Под четыре реальных запроса:

- `(board_id, stage_id)` — доска;
- `(assignee_id)` частичный, `WHERE closed_at IS NULL` — «мои открытые»;
- `(student_id)` частичный, `WHERE student_id IS NOT NULL` — блок на странице ученика;
- `(due_date)` частичный, `WHERE closed_at IS NULL` — недельный вид и просрочка.

## 6. Правила поведения

**Задача закрыта тогда и только тогда, когда её стадия имеет категорию
`closed`.** Единственный источник истины — стадия. Отдельного флага «выполнено»
в данных нет.

- Перенос в закрытую стадию **требует** указать результат; без него — ошибка
  валидации.
- Перенос из закрытой стадии в открытую **обнуляет** `resolution` и `closed_at`.
- Кнопка «Выполнено» — не флаг, а **действие**: переносит карточку в первую по
  порядку стадию категории `closed` внутри её воронки и спрашивает результат.
  Для пользователя это один клик из любой колонки, как в WEEEK; в данных
  двусмысленности не возникает.
- Воронка выбирается при создании и остаётся свойством карточки (как проект в
  Jira).
- Штатный способ убрать ненужную задачу — закрыть с результатом `irrelevant`.
  Физическое удаление доступно только роли `admin`.
- **Смена категории у стадии с задачами запрещена** (409 `has_tasks`). Иначе
  карточки оказались бы в закрытой колонке с пустыми `closed_at`/`resolution`,
  то есть два определения «закрыта» — доктрина (категория стадии) и данные, на
  которые смотрят фильтры, просрочка и индексы, — разошлись бы. CHECK в БД это
  не ловит: он связывает `closed_at` и `resolution` между собой, но не со
  стадией. Штатный путь: завести новую стадию и перенести карточки через
  `move_task`.
- **Переупорядочивание стадий требует полный набор стадий воронки** (иначе 400):
  неполный набор раздал бы позиции, конфликтующие с нетронутыми стадиями.
- **Воронку с задачами удалить нельзя.** Стадии удаляются каскадом вслед за
  воронкой, а задачи держат стадию через `RESTRICT` — то есть на уровне БД
  удаление всё равно упало бы с ошибкой внешнего ключа. Сервис проверяет это
  заранее и отдаёт понятную ошибку, предлагая архивирование (`is_archived`).

Каждая смена стадии, смена исполнителя и комментарий пишут запись в
`TaskActivity`.

## 7. API

База — `/api/admin/tasks`, без завершающего слэша (`APPEND_SLASH=False`).

```
GET  /api/admin/tasks                     список с фильтрами (пагинация)
POST /api/admin/tasks                     создать
GET  /api/admin/tasks/boards              воронки
POST /api/admin/tasks/boards              создать воронку
PATCH|DELETE /api/admin/tasks/boards/<id>
GET  /api/admin/tasks/boards/<id>/stages  стадии воронки
POST /api/admin/tasks/boards/<id>/stages
PATCH|DELETE /api/admin/tasks/stages/<id>
POST /api/admin/tasks/stages/reorder      порядок колонок
GET  /api/admin/tasks/boards/<id>/columns колонки доски со счётчиками (без карточек)
GET  /api/admin/tasks/columns/<stage_id>  карточки одной колонки (пагинация)
GET  /api/admin/tasks/week?date_from=&date_to=[&фильтры]  недельный вид
GET  /api/admin/tasks/assignees           справочник исполнителей (manager/admin)
GET|POST /api/admin/tasks/tags
PATCH|DELETE /api/admin/tasks/tags/<id>
GET|POST /api/admin/tasks/types
PATCH|DELETE /api/admin/tasks/types/<id>
GET|PATCH /api/admin/tasks/<pk>
POST /api/admin/tasks/<pk>/move           перенос в стадию (+ resolution при закрытии)
POST /api/admin/tasks/<pk>/complete       кнопка «Выполнено»
POST /api/admin/tasks/<pk>/comment
GET  /api/admin/tasks/<pk>/activity
```

Литеральные пути (`/boards`, `/stages`, `/columns`, `/week`, `/tags`, `/types`)
объявляются **до** `/<int:pk>` — как в `apps/renewals/urls.py`.

Задачи по ученику отдельного маршрута не получают: это фильтр `?student_id=` на
коллекции. Меньше сущностей, один код фильтрации, одна проверка прав.

Фильтры коллекции: `board_id`, `stage_id`, `assignee_id`, `student_id`,
`group_id`, `priority`, `task_type_id`, `tag_id`, `only_open`, `overdue`,
`q` (поиск по заголовку). Те же фильтры принимает и недельный вид — фильтр-бар
на странице общий для обоих представлений. Значения проверяет
`TaskFilterSerializer`: мусор даёт 400, а не 500 из ORM.

Пагинация — ОБЩИЙ пагинатор проекта `apps.core.pagination.StandardPagination`,
конверт `{rows, total, page, page_size}`. Дефолтный конверт DRF в этом проекте
не используется нигде.

## 8. Права доступа

DRF по умолчанию `AllowAny` — **каждая вьюха обязана задать
`permission_classes` явно**.

- **Карточки** (список, создание, деталь, перенос, «Выполнено», комментарии,
  лента, справочники на чтение): `IsManagerOrAdmin`.
- **Структура** (воронки, стадии, теги, типы — создание, переименование,
  порядок, удаление): `ReadStaffWriteSuperAdmin`. Тот же класс, что охраняет
  стадии продлений: менеджер работает внутри процесса, но не переопределяет
  сам процесс.
- **Физическое удаление задачи**: `IsAdminOrSuperAdmin`.
- Преподаватель (`role='teacher'`) не имеет доступа ни к чему в разделе.

Менеджер видит **все** задачи, а не только свои: в админке 10–15 человек,
скрывать нечего, а «показать только мои» — фильтр интерфейса, не право доступа.

## 9. Интерфейс (admin SPA)

Новый раздел «Задачи» в меню. На странице: выбор воронки, переключатель
**Доска / Неделя**, фильтр-бар (исполнитель, ученик, приоритет, тег, «только
открытые»).

- **Доска** — колонки-стадии со счётчиком в заголовке, перетаскивание карточек,
  поле «Добавить задачу» вверху колонки для быстрого создания одним заголовком.
  Закрытая задача — зачёркнутый заголовок с галочкой.
- **Неделя** — те же карточки, колонки-дни по `due_date`, перелистывание недель.
  Задачи без срока в этот вид не попадают.
- **Панель справа** по клику на карточку — по образцу `RenewalDrawer.tsx`, не
  модальное окно.
- **Настройка воронок и стадий** — отдельная страница по образцу
  `RenewalStagesSettings.tsx`.
- **Страница ученика** — блок «Задачи»: открытые списком, закрытые под свёрткой.

Обязательное по регламенту проекта: только `SelectInput` / `DateInput` /
`Checkbox` / `Combobox` из `components/form` (нативные form-элементы
запрещены); подписи перечислений — только из `lib/labels.ts`; цвета, радиусы и
отступы — только через токены `tokens.css`; `placeholderData: keepPreviousData`
во всех серверно-пагинированных хуках; `ErrorBoundary` с
`key={location.pathname}`; `.data-table--loading` гасит `pointer-events` только
на `tbody`.

## 10. Производительность

VPS 4 CPU / 6 ГБ, 10–15 одновременных пользователей админки.

- **Доска не грузится одним запросом.** Список колонок со счётчиками — один
  лёгкий агрегат; карточки каждой колонки — отдельный пагинированный запрос
  (`/columns/<stage_id>`), как `RenewalColumnCardsView` сейчас. Иначе воронка с
  тысячей закрытых задач кладёт страницу.
- `select_related` на `assignee`, `created_by`, `student`, `group`, `stage`;
  `prefetch_related` на теги — иначе каждая карточка даёт лишние запросы.
- Недельный вид — один запрос с диапазоном по `due_date`, опирается на
  частичный индекс.

## 11. Журнал изменений (pghistory)

Все доменные модели получают
`@pghistory.track(InsertEvent(), UpdateEvent(), DeleteEvent())` + запись в
`apps/changelog/registry.py` в топологическом порядке:

| Модель | entity | revertable | topo |
|---|---|---|---|
| `taskboard.TaskBoard` | `task_board` | да | 10 |
| `taskboard.TaskType` | `task_type` | да | 10 |
| `taskboard.TaskTag` | `task_tag` | да | 10 |
| `taskboard.TaskStage` | `task_stage` | да | 20 |
| `taskboard.Task` | `task` | да | 30 |
| `taskboard.TaskActivity` | `task_activity` | нет | 40 |

Лента активности неоткатываема: это лог, откатывать в нём нечего.

Плюс правила меток в `apps/changelog/labels.py` на новые мутирующие маршруты:
создание задачи, перенос, «Выполнено», комментарий, правка воронки, стадий,
тегов и типов.

Тест `test_registry_covers_all_tracked_models` покраснеет, если запись забыта.

## 12. Точка расширения под автогенерацию

Всё создание задач проходит через **одну сервисную функцию** в
`apps/taskboard/services.py`, а не через сериализатор напрямую. Когда позже
появится первое автоматическое правило («абонемент кончился — позвонить»), оно
вызовет ту же функцию.

Ключ дедупликации (`dedup_key`), защищающий от размножения одинаковых
автозадач, **сейчас не добавляется**: он нужен только автоправилам, которых нет,
а таблица задач маленькая — добавить колонку с уникальным индексом позже так же
дёшево, как сейчас.

## 13. Тесты

Всё на pytest. **После миграций гонять полный `pytest -q`, а не по
приложениям**: часть приложений no-op'ит `django_db_setup` (общая
`journal_test`), часть пересоздаёт `test_journal_test` — прогон по частям даёт
ложно-зелёный результат.

- **Ограничения БД**: категория только из перечня; формат цвета; уникальность
  названия стадии внутри воронки; `RESTRICT` не даёт удалить стадию с задачами;
  воронку с задачами удалить нельзя.
- **Права**: каждая ручка под каждой ролью — преподаватель 403 везде; менеджер
  работает с карточками, но не правит стадии; структура только суперадмину;
  физическое удаление только админу.
- **Правила закрытия**: перенос в закрытую стадию без результата отклоняется;
  возврат в открытую обнуляет `resolution` и `closed_at`; «Выполнено» уводит в
  первую закрытую стадию воронки; удаление последней открытой (или последней
  закрытой) стадии воронки запрещено.
- **Фильтры и пагинация**: по исполнителю, ученику, группе, приоритету, тегу,
  «только открытые», «просроченные».
- **Недельный вид**: границы диапазона включительно; задачи без срока не
  попадают.
- **Лента**: смена стадии, смена исполнителя и комментарий создают записи.

## 14. Порядок работ

Пять этапов, каждый заканчивается зелёным полным прогоном `pytest -q`:

1. **Модели и схема.** Приложение, шесть моделей, миграции, триггеры pghistory,
   data-миграция со стартовой воронкой «Общие задачи» (стадии «Новая»,
   «В работе» — `open`; «Готово» — `closed`), записи в реестре журнала
   изменений.
2. **API карточек.** Коллекция с фильтрами, деталь, перенос, «Выполнено»,
   комментарии, лента, справочники. Права и тесты.
3. **API структуры.** Воронки, стадии, теги, типы; переупорядочивание;
   валидация «нельзя удалить последнюю стадию категории».
4. **Фронтенд: доска.** Раздел в меню, выбор воронки, колонки, перетаскивание,
   панель справа, быстрое добавление, страница настроек воронок и стадий.
5. **Фронтенд: неделя и ученик.** Переключатель вида «Неделя», блок задач на
   странице ученика.

Первые три этапа дают работающий бэкенд, проверяемый до написания интерфейса.
