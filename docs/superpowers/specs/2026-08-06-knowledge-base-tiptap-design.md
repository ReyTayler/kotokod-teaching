# База знаний на TipTap — дизайн

Дата: 2026-08-06
Статус: утверждён, не реализован

Раздел «База знаний» в admin SPA: создание и редактирование внутренней
документации компании, с настройкой прав на чтение по ролям и картинками.

## Требования

1. Создание документа.
2. Редактирование документа.
3. Права на чтение по ролям системы.
4. Читаемый вид на чтение — нормально свёрстанная страница документа
   (человекочитаемость — это вид на экране, а не содержимое колонки в дампе).
5. Картинки внутри документов, с оптимизацией.
6. Неблокирующий I/O: воркер gunicorn не занимается перекодированием картинок
   и не перекачивает файлы через Python.

## Решения по объёму

| вопрос | решение |
|---|---|
| структура | разделы → документы, ровно два уровня |
| права на чтение | явный набор ролей на каждом документе |
| права на запись | только `admin` / `superadmin` |
| жизненный цикл | черновик → публикация |
| аудитория v1 | admin SPA; teacher SPA — отдельный этап |
| картинки | да, с оптимизацией вне запроса |

Чего в v1 сознательно нет: истории версий, полнотекстового поиска,
автосохранения, комментариев, совместного редактирования, экспорта,
вложений-файлов, раздела в teacher SPA.

Модель данных заранее готова к двум из них: `plain_text` — фундамент под поиск,
`reader_roles` включает `teacher` — фундамент под teacher SPA. Добавление не
потребует менять схему.

## Выбор технологии

TipTap 3.29.2, лицензия MIT, `peerDependencies` включают React 19 — совместим с
текущим фронтом admin SPA (React 19 + Vite 8). Всё из требований 1–5 закрывается
бесплатной частью; платные Pro-расширения (совместное редактирование через облако
TipTap, комментарии, AI, история версий, импорт/экспорт docx) не используются.

### Форма хранения и рендера

Рассмотренные варианты:

| | Что храним | Рендер читателю | XSS | Вес для читателя |
|---|---|---|---|---|
| **A (выбран)** | `jsonb` с TipTap-JSON | `@tiptap/static-renderer` → React-элементы | нет по построению | ~15–25 КБ |
| B | `jsonb` + денормализованный HTML | `dangerouslySetInnerHTML` | нужен санитайзер на сервере | ~0 |
| C | Markdown в `text` | markdown-парсер на клиенте | есть (raw HTML в MD) | ~40 КБ |

Выбран **A**. Единственный источник правды, схема ровно та, которую редактор
умеет читать и писать. На чтении HTML не собирается из строки, поэтому
санитайзер не нужен вовсе. Пакет `@tiptap/static-renderer` рендерит JSON в
React-элементы без загрузки ProseMirror — читатель не тянет редактор.

Безопасность обеспечивается не санитайзером на выходе, а валидацией на входе:
белый список типов узлов и марок (см. `content.py` ниже).

### Хранение картинок

| | Хранение | Отдача | Оптимизация |
|---|---|---|---|
| **A (выбран)** | файл в `MEDIA_ROOT`, метаданные в БД | `X-Accel-Redirect`, байты пушит nginx | Celery: WebP + ресайз |
| B | `bytea` в PostgreSQL | стримит Python | раздувает БД и дампы |
| C | внешнее S3-совместимое | прямая ссылка | нужен новый сервис + правка CSP `img-src` |

Выбран **A**. Он же отвечает на требование неблокирующего I/O.

## Модель данных

Новое приложение `journal_django/apps/knowledge/` со стандартной для проекта
раскладкой: `models.py` → `repository.py` → `services.py` → `content.py` →
`serializers.py` → `permissions.py` → `views.py` → `urls.py` → `tasks.py` →
`tests/`.

**pghistory на моделях раздела не ставится** — решение пользователя. Проверено:
тест `test_registry_covers_all_tracked_models` сравнивает множества симметрично
(`tracked_in_db == set(registry.TRACKED.keys())`), поэтому нетрекаемая модель его
не роняет. Записей в `apps/changelog/registry.py` не добавляем.

### `knowledge_sections`

| поле | тип | смысл |
|---|---|---|
| `id` | serial PK | |
| `title` | text unique | «Методика», «Продажи» |
| `position` | int | ручной порядок |
| `active` | bool default true | мягкое удаление, как у `directions` |
| `created_at` / `updated_at` | timestamptz | |

Удаление раздела с документами → `409 {error: 'has_documents'}` (паттерн
`directions` при наличии оплат). Считаются только активные документы: раздел, где
все документы мягко удалены, удаляется без возражений.

### `knowledge_documents`

| поле | тип | смысл |
|---|---|---|
| `id` | serial PK | |
| `section_id` | FK → `knowledge_sections`, `PROTECT` | |
| `title` | text | |
| `content` | jsonb | TipTap-JSON, источник правды |
| `plain_text` | text | плоский текст, вынимается сервером из `content` |
| `status` | text | `draft` / `published`, CHECK |
| `reader_roles` | text[] | кто читает; CHECK `contained_by` списка ролей |
| `position` | int | порядок внутри раздела |
| `published_at` | timestamptz null | |
| `created_by_id` / `updated_by_id` | FK → `accounts`, `SET_NULL` | |
| `active` | bool default true | мягкое удаление |
| `created_at` / `updated_at` | timestamptz | |

Инварианты:

1. **`admin` и `superadmin` видят всё** — черновики и документы с пустым
   `reader_roles` включительно. `reader_roles` управляет доступом только для
   `teacher` и `manager`. Без этого документ теряется, если снять все галочки.
2. **`content` — это `TolerantJSONField`**, не штатный `JSONField`. Проект
   глобально регистрирует jsonb-typecaster psycopg2 (`apps/core/apps.py`), и
   штатный `JSONField` на чтении падает с «the JSON object must be str, not dict».
   См. `apps/core/db_fields.py`.
3. **`plain_text` пишет сервер**, а не клиент — рекурсивным обходом текстовых
   узлов `content` при каждом сохранении.

Индексы: `(section_id, position) WHERE active`, GIN по `reader_roles`,
частичный по `status = 'published'`.

### `knowledge_images`

| поле | тип | смысл |
|---|---|---|
| `id` | serial PK | |
| `sha256` | char(64) unique | контент-адресация и дедупликация |
| `original_name`, `mime`, `byte_size`, `width`, `height` | | метаданные |
| `original_path` | text | путь относительно корня медиа |
| `optimized_path`, `thumb_path` | text null | появляются после Celery-задачи |
| `optimize_state` | text | `pending` / `ready` / `failed` |
| `uploaded_by_id` | FK → `accounts`, `SET_NULL` | |
| `created_at` | timestamptz | |

### `knowledge_image_usages`

| поле | тип |
|---|---|
| `image_id` | FK → `knowledge_images`, `CASCADE` |
| `document_id` | FK → `knowledge_documents`, `CASCADE` |

`unique(image_id, document_id)`.

Таблица пересобирается сервисом при каждом сохранении документа: обход `content`,
сбор `imageId` всех узлов `image`, синхронизация набора. Решает две задачи:

- **права**: запрос картинки разрешён, если у запрашивающего есть доступ хотя бы
  к одному документу, где она используется. Без этого прямая ссылка на файл
  утекает мимо ролевой модели, а «неугадываемый путь» — не защита;
- **уборка**: картинка без единого usage становится кандидатом на удаление.

## API

Монтируется в `config/urls.py`:
`path('api/admin/knowledge', include('apps.knowledge.urls'))` — среди прочих
`/api/admin/*`, то есть выше teacher-guard. Порядок mount не нарушается.

### Разделы

```
GET    /api/admin/knowledge/sections
POST   /api/admin/knowledge/sections
PATCH  /api/admin/knowledge/sections/:id
DELETE /api/admin/knowledge/sections/:id        → 409 has_documents
POST   /api/admin/knowledge/sections/reorder
```

### Документы

```
GET    /api/admin/knowledge/documents?section_id=&status=   ← без content, пагинация DRF
POST   /api/admin/knowledge/documents
GET    /api/admin/knowledge/documents/:id                   ← с content
PATCH  /api/admin/knowledge/documents/:id
DELETE /api/admin/knowledge/documents/:id                   ← мягкое
POST   /api/admin/knowledge/documents/:id/publish
POST   /api/admin/knowledge/documents/:id/unpublish
POST   /api/admin/knowledge/documents/reorder
```

### Картинки

```
POST   /api/admin/knowledge/images                          ← multipart, 201 {id, state:'pending'}
GET    /api/admin/knowledge/images/:id?variant=optimized|thumb|original
```

`variant` по умолчанию — `optimized`. Неизвестное значение → `400`.

### Права

Permission-класс решает «кого пускать в эндпоинт», сервис — «что показывать».

- `KnowledgeReadStaffWriteAdmin` в `apps/knowledge/permissions.py`: SAFE-методы —
  любая аутентифицированная роль (включая `teacher`, чтобы на втором этапе не
  переделывать бэк); мутации — `admin` / `superadmin`.
- Фильтрация в репозитории: `admin` / `superadmin` получают всё; остальные —
  `status = 'published' AND active AND reader_roles @> ARRAY[<своя роль>]`.
  Условие уходит в SQL и попадает в GIN-индекс, никаких Python-циклов.
- На detail-запрос недоступного документа — **404, а не 403**. 403 сообщил бы о
  существовании документа с таким id.
- Загружать картинки может только `admin` / `superadmin` — тот же круг, что пишет
  документы.

DRF default — `AllowAny`, поэтому каждая вьюха раздела обязана объявить
`permission_classes` явно.

### Валидация контента — `apps/knowledge/content.py`

Чистые функции без обращения к БД:

- белый список типов узлов и марок; неизвестный тип → `400 invalid_content`;
- лимит сериализованного JSON — 512 КБ, лимит глубины вложенности — 20;
- проверка, что каждый узел `image` ссылается на существующую запись
  `knowledge_images` (проверка принимает набор допустимых id аргументом, сам
  модуль в БД не ходит);
- `extract_plain_text(content) -> str`.

Модуль тестируется отдельно от вьюх и держит инвариант «в БД не попадает JSON,
который рендерер не умеет показать».

### Неблокирующий I/O — по точкам

| точка | что делает воркер | чего не делает |
|---|---|---|
| `POST /images` | пишет файл на диск чанками, считает sha256 потоково, ставит задачу Celery | не декодирует, не жмёт, не ресайзит |
| `GET /images/:id` | проверяет права → пустой ответ с `X-Accel-Redirect` | не читает файл, не гонит байты через Python |
| `PATCH /documents/:id` | одна транзакция: документ + пересборка usages | ничего тяжёлого |
| `GET /documents` | пагинация DRF, `content` не выбирается из БД | не тянет мегабайты jsonb в список |

## Пайплайн изображений

**В JSON хранится id, а не URL.** Узел `image` несёт атрибут `imageId`; `src`
собирается при рендере как `/api/admin/knowledge/images/<id>?variant=optimized`.
Смена схемы раздачи не потребует переписывать содержимое документов.

**Раскладка на диске** — контент-адресная:

```
$KNOWLEDGE_MEDIA_ROOT/knowledge/ab/cd/<sha256>.<ext>          оригинал
$KNOWLEDGE_MEDIA_ROOT/knowledge/ab/cd/<sha256>.w1600.webp     основной вариант
$KNOWLEDGE_MEDIA_ROOT/knowledge/ab/cd/<sha256>.w400.webp      превью
```

Два уровня вложенности по первым четырём hex-символам — чтобы в одном каталоге не
скопились десятки тысяч файлов. Корень берётся из окружения
(`KNOWLEDGE_MEDIA_ROOT`), в git не попадает.

**Дедупликация на загрузке**: посчитали sha256 → если запись есть, временный файл
выбрасываем и отдаём существующий id. Один скриншот в пяти документах занимает
место один раз.

**Celery-задача `optimize_image(image_id)`**:

1. разворот по EXIF-ориентации (иначе фото с телефона лежит боком);
2. **удаление EXIF целиком** при сохранении — в нём геотеги и модель устройства;
3. ресайз до 1600px по длинной стороне (WebP, q≈82) и превью 400px;
4. `optimize_state = 'ready'`.

Типичный скриншот 2.5 МБ PNG → 150–250 КБ WebP.

**Пока не готово — отдаём оригинал.** Запрос `?variant=optimized` при
`state != 'ready'` прозрачно возвращает исходный файл. Следствие: при
недоступных Redis/Celery (штатная локальная ситуация) раздел работает, просто без
сжатия. Плюс management-команда, чтобы догнать зависшие в `pending`.

**Что принимаем**: PNG, JPEG, WebP. Тип определяется Pillow по содержимому,
расширению не верим.

- **SVG запрещён** — это XML со встраиваемым скриптом; отдача с нашего origin
  обошла бы CSP;
- лимит по пикселям (~50 Мп) против декомпрессионных бомб: 2 МБ файла могут
  развернуться в гигабайты RAM, а на VPS её 2 ГБ;
- лимит размера файла 10 МБ + DRF-throttling на загрузку.

**Кэширование на отдаче**: `ETag` = sha256 (содержимое по id неизменно по
построению), `Cache-Control: private, max-age=86400`. Именно `private` — файл не
должен осесть в общем прокси мимо проверки прав.

**Уборка**: периодическая задача удаляет записи без единого usage старше 7 дней.
Отсрочка нужна, потому что картинка появляется при загрузке, а в документ
попадает при сохранении; немедленное удаление ломало бы черновики.

**nginx**: `internal`-локация для медиа-корня и `client_max_body_size` на
загрузку. Правки — в оба конфига, боевой (`deploy/nginx/journal-kotokod.conf`) и
локальный (`deploy/nginx/local/nginx.conf`), они держатся синхронно.

CSP не меняется: файлы отдаются с того же origin, `img-src 'self'` уже разрешает.

## Admin SPA

**Навигация**: отдельный пункт «База знаний» в сайдбаре, видимый всем ролям
админки. Кнопки создания и правки — по `can`-предикату, как у «Зарплаты» и
«Учёток». Это UX-слой; настоящая защита на API.

**Маршруты**:

```
/admin/knowledge            список: разделы слева, документы раздела справа
/admin/knowledge/:id        чтение документа
/admin/knowledge/:id/edit   редактор, обёрнут RequireRole(admin|superadmin)
```

**Разделение чтения и правки**. `DocumentView` рендерит через
`@tiptap/static-renderer`: TipTap-JSON → React-элементы, без ProseMirror и без
`dangerouslySetInnerHTML`. `DocumentEditor` подключается через `React.lazy` и
уезжает в отдельный чанк Vite. Менеджер, читающий регламент, не тянет ~150 КБ
редактора, который ему запрещён.

**Состав редактора** (всё MIT): `StarterKit` (заголовки, списки, цитаты, код,
ссылки), `Table`, `Placeholder`, собственное расширение `KnowledgeImage` с
атрибутом `imageId`. Тулбар — на существующих `Button` / `ui`-компонентах;
настройка прав — `Checkbox` из `components/form/`, лейблы ролей из
`lib/labels.ts`. Native form-элементы в админке запрещены.

**Стили** — `styles/knowledge.css` целиком на токенах из `tokens.css`.
Типографика статьи (заголовки, интерлиньяж, таблицы, блоки кода) — новый набор
классов, но ни одного захардкоженного цвета или отступа.

**Данные** — `hooks/useKnowledge.ts` на TanStack Query, во всех списочных хуках
`placeholderData: keepPreviousData`.

**Сохранение** — явной кнопкой. Автосохранения в v1 нет, поэтому нужна защита от
потери: блокировка ухода с несохранёнными правками через `useBlocker`
(React Router 7) плюс `beforeunload`.

**Загрузка картинки**: drag-and-drop или вставка из буфера в редактор → `POST` →
узел с `imageId`. Ошибка — тост (Radix toast уже в проекте).

## Обработка ошибок

| ситуация | ответ API | UI |
|---|---|---|
| неизвестный тип узла в JSON | `400 invalid_content` | тост «Документ содержит неподдерживаемый блок» |
| файл больше 10 МБ | `413` | тост с указанием лимита |
| не картинка или SVG | `415` | тост «Поддерживаются PNG, JPEG, WebP» |
| нет доступа к документу | `404` | страница «Документ не найден» |
| удаление непустого раздела | `409 has_documents` | диалог «Сначала перенесите или удалите документы» |

## Тестирование

pytest, ядро — матрица прав: роль (`teacher` / `manager` / `admin` /
`superadmin`) × `status` × `reader_roles`, на список и на detail.

Отдельно:

- валидатор контента: белый список, лимит размера, лимит глубины, ссылка на
  несуществующую картинку;
- `extract_plain_text` на вложенных структурах;
- дедупликация по sha256 (повторная загрузка того же файла → тот же id);
- пересборка `usages` при сохранении (добавление и удаление картинки из текста);
- наличие заголовка `X-Accel-Redirect` и отсутствие тела в ответе;
- 404 вместо 403 на недоступном документе;
- 409 на удалении раздела с документами;
- отказ на SVG и на файле сверх лимита;
- фолбэк на оригинал при `optimize_state != 'ready'`.

Прогон — **полным** `pytest -q`, не по приложениям: часть приложений no-op'ит
`django_db_setup` (общая `journal_test`), часть пересоздаёт `test_journal_test`,
и прогон по частям даёт ложнозелёный результат.

Фронт: `npm run typecheck` и ручной браузерный прогон.
