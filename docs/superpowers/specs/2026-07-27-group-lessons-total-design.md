# Спека: ручная длина курса группы (`groups.lessons_total`)

Дата: 2026-07-27.

**Цель:** дать менеджеру задать в форме группы, сколько уроков эта группа должна
отходить, вместо жёсткой привязки к `direction.total_lessons`. Основной сценарий —
ученик начинает обучение не с первого урока курса (прошёл часть в другой группе),
под него заводится группа, которая должна отходить только остаток.

**Принцип:** одно необязательное число на группе. Пусто — поведение ровно как
сегодня. Никаких новых сущностей, никакого влияния на деньги.

---

## 1. Проблема

Сейчас длина курса группы выводится из направления, и обойти это нечем. Из-за
этого сценарий «ученик стартует с 35-го урока» не собирается ни одним из доступных
путей:

- **Пометки «неоплачиваемый пропуск» на уроки 1–34.** Пометка говорит «этого
  ученика на уроке нет», но не двигает его счётчик `lessons_done`. Кабинет
  преподавателя считает номер очередного урока как «счётчик + шаг»
  (`apps/teacher_spa/services.py`), поэтому он всё равно предложит урок №1. Если
  ученик в группе один, уроки 1–34 проводить некому — отмечать нечего.
- **Старт группы задним числом + смена расписания с 35-го урока.** План
  разворачивается на весь курс направления, уроки 1–34 встают на прошлые даты и
  остаются пустыми. `has_unfilled_before` (`apps/scheduling/repository.py`)
  запрещает отмечать урок, пока есть незаполненное занятие с более ранней плановой
  датой → преподаватель заблокирован навсегда, а вкладка «Заполнить» показывает
  34 долга.
- **Ручной старт-оффсет** (`lesson_number_offset` + seed `lessons_done`) в коде
  есть, но проставляется только автоматикой перевода; ручной вход удалён
  2026-07-24 вместе с `POST /memberships/place`.

## 2. Принятая модель

**Номер урока — локальный счётчик группы.** Группа-остаток нумерует свои занятия
с 1. Позиция ученика в программе отслеживается на уровне направления: прогресс в
карточке ученика суммирует посещения по всем его группам направления, знаменатель —
`direction.total_lessons` (`apps/students/repository.py::student_stats`). Ученик,
прошедший 34 урока в прежней группе и 2 в группе-остатке, увидит 36 из 36.

Из этого следует: `lesson_number_offset` в этой фиче НЕ используется и не
выставляется. Пометки пропусков для этого сценария больше не нужны.

## 3. Модель данных

`groups.lessons_total` — `IntegerField(null=True, blank=True)`, CHECK `> 0`.

- `NULL` — «как в направлении» (текущее поведение, дефолт для всех существующих
  групп; миграция ничего не засевает).
- Заполнено — группа планируется на это число уроков.
- Единица измерения — **уроки курса**, как у `direction.total_lessons`, а НЕ
  календарные занятия. У 45-минутной группы шаг 0.5, поэтому 2 урока = 4 занятия
  с номерами 0.5, 1.0, 1.5, 2.0.

Обязательства по конвенциям: миграция; `Group` уже под `@pghistory.track` →
перегенерация триггеров; подпись поля в `apps/changelog/summary.py`
(`'lessons_total': 'уроков в группе'`). Правило `group.update` в
`apps/changelog/labels.py` уже покрывает `PATCH /api/admin/groups/<id>` — новых
правил не нужно.

## 4. Эффективная длина курса

Вводится единственная функция «эффективная длина курса группы» =
`COALESCE(group.lessons_total, direction.total_lessons)`. Через неё идут все места,
где длина курса нужна для **плана и сетки**:

| Место | Что делает |
|---|---|
| `apps/scheduling/repository.py::generate_for_group` | генерация плана |
| `apps/scheduling/repository.py::permanent_change` | «изменить расписание» — разворот хвоста курса |
| `apps/scheduling/repository.py::rebuild_from_facts` / `_build_rebuild_rows` | пересборка плана из фактов |
| `apps/scheduling/repository.py::active_groups` | список групп для календаря и бэкфилла |
| `apps/groups/repository.py::get_group_progress` | число клеток сетки |
| `apps/teacher_spa/views.py::GroupDirectionsView` | лимит курса в кабинете преподавателя (карточка группы, форма урока) |
| `frontend/admin-src/src/components/lessons/LessonGrid.tsx` | число клеток сетки занятий (считается на клиенте, не из API прогресса) |

**Не трогаем** (остаются на направлении):

- лимит продаж `apps/payments/repository.py::create_payment` — иначе ученику
  группы-остатка нельзя будет продать больше двух уроков;
- прогресс ученика `apps/students/repository.py::student_stats` и «Реестр»
  `apps/dashboard/registry_service.py` — прогресс по программе считается по
  направлению (раздел 2).

## 5. Поведение плана при изменении числа

Правка `lessons_total` подгоняет план в той же транзакции, что и сохранение группы
(`apps/groups/repository.py::update_group`):

- **Увеличили** — недостающие позиции дописываются в хвост от последней плановой
  даты по текущим открытым слотам (`planner.generate` со `start_seq`/`start_number`
  от последней строки). Существующие строки, переносы и замены не трогаются.
- **Уменьшили** — курсовые строки за пределами нового числа удаляются с конца,
  **только** `pending`/`overdue`. `done` и `moved` не удаляются никогда. Маркеры
  отмены (`seq IS NULL`) к курсу не относятся и не трогаются.
- **Отказ** — если за границей нового числа осталась хоть одна строка `done`/`moved`:
  409 с сообщением «в группе уже проведено N занятий». Молча резать проведённое
  нельзя.
- **Плана ещё нет** — поле просто сохраняется, подгонять нечего; план построит
  кнопка «Сгенерировать план».
- Сравнение «сколько уже проведено» ведётся **в уроках** (сумма шагов), не в штуках
  строк: на 45-минутной группе 4 занятия = 2 урока.

При создании группы поле просто сохраняется; план генерируется существующей
кнопкой «Сгенерировать план», как сейчас.

## 6. API и валидация

- `GroupWriteSerializer` / `GroupUpdateSerializer`: `lessons_total`
  `IntegerField(min_value=1, allow_null=True, required=False)`.
- `NULL` присылается явно, чтобы вернуться к наследованию от направления.
- Чтение: `lessons_total` в `_GROUP_FIELDS` → уезжает на фронт вместе с группой.
- RBAC не меняется (эндпоинты групп уже `IsManagerOrAdmin`).

## 7. Интерфейс

- Форма группы (создание и правка): `NumberInput` из `components/form/`
  (native-элементы запрещены), подпись «Уроков в группе», плейсхолдер
  «как в направлении (36)».
- Подсказка под полем для 45-минутного формата: «2 урока = 4 занятия по 45 мин».
- Карточка группы: показывать действующее число уроков и признак, что оно задано
  вручную (иначе непонятно, почему план короче курса).
- Дизайн-токены, `lib/labels.ts` — по конвенции проекта.

## 8. Тесты

- план: `lessons_total=2` → ровно 2 занятия, номера 1, 2;
- 45 мин: `lessons_total=2` → 4 занятия, номера 0.5 … 2.0;
- фолбэк: `NULL` → план как от направления (регресс);
- увеличение: дописан хвост, существующие строки/переносы не тронуты;
- уменьшение: удалены только непроведённые хвостовые строки;
- отказ: новое число меньше проведённых уроков → 409, план не изменился;
- сетка: число клеток считается от эффективной длины (вкл. 45 мин);
- регресс: лимит продаж и прогресс ученика по направлению не изменились;
- changelog: правка поля попадает в журнал изменений с читаемой подписью.

Гейт: полный `pytest -q` (не по частям — см. память
`project_test_db_django_db_setup_split`), typecheck admin SPA, браузерный смоук.

## 9. Риски

1. **Единицы измерения.** Самый вероятный источник ошибок — спутать уроки и
   занятия на 45-минутном формате. Каждое сравнение и срез хвоста — через шаг.
2. **Удаление хвоста плана.** Затронуть `done` или строки с ручными переносами =
   потеря данных. Резать строго по статусу.
3. **Расползание поля.** Соблазн подставить длину группы в лимит оплат или в
   прогресс по направлению. Явно запрещено разделом 4.

## 10. Что делать с ПГ300 после внедрения

Задать «2 урока», снять 34 пометки «неоплачиваемый пропуск» (они лягут на новые
клетки 1 и 2 и вычеркнут ученика), сгенерировать план. Дальше группа живёт обычной
жизнью: занятия 1 и 2 на реальных датах, счётчик ученика идёт с нуля, прогресс по
направлению — 36 из 36 вместе с прежней группой.
