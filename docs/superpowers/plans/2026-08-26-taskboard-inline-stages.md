# Настройка стадий прямо на доске задач — план

Дата: 2026-08-26
Основание: референс заказчика (меню `⋯` в шапке колонки + плитка «Добавить колонку»).
Предшественник: [`2026-08-26-taskboard-redesign.md`](2026-08-26-taskboard-redesign.md).

**Цель:** править стадии воронки не уходя со страницы — переименовать, покрасить,
переставить, удалить и добавить колонку прямо на доске.

**Из бэкенда меняются права и маршрут перестановки** (Задачи 0 и 0b). Остальное уже есть
и покрыто тестами:

| Действие | Эндпоинт |
|---|---|
| Создать стадию | `POST /api/admin/tasks/boards/<board_id>/stages` |
| Переименовать / покрасить / сменить вид | `PATCH /api/admin/tasks/stages/<pk>` |
| Переставить | `POST /api/admin/tasks/boards/<board_id>/stages/reorder` (переезжает, Задача 0b) |
| Удалить | `DELETE /api/admin/tasks/stages/<pk>` |

Коды конфликтов (`has_tasks`, `last_stage_of_category`, `duplicate_label`,
`incomplete_stage_set`, `unknown_stage`) уже переведены в `TASK_CONFLICT_LABELS`
и разбираются существующим `conflictError` из `TaskBoard.tsx`.

---

## Что делаем

### 1. Меню `⋯` в шапке колонки

`BoardColumnHead` (общий с «Продлениями») уже принимает слот `actions` — менять его не надо,
достаточно передать меню из `TaskColumn`. Пункты через существующий `ActionMenu`:

- **Переименовать** — правка названия на месте, как заголовок задачи в панели: подпись
  превращается в `TextInput` по клику, Enter/blur сохраняют.
- **Настройки** — маленький `Dialog`: цвет (набор образцов, как в `TaskStagesSettings`) и вид
  стадии (открытая / закрытая).
- **Сдвинуть влево** / **Сдвинуть вправо** — по одному шагу. Крайние пункты скрыты.
- **Удалить** — через `ConfirmModal`.

### 2. Плитка «Добавить колонку»

Последним элементом ленты доски, приглушённая, по клику — поле названия (тот же приём, что
«+ Добавить задачу» внизу колонки). Новая стадия создаётся открытой (`category: 'open'`),
цвет пустой — тон выведется из названия через `stageTone`.

### 3. Чего НЕ делаем

- **Дублировать** — копия стадии всегда пустая, а название всё равно вводить руками: то же
  самое, что «Добавить колонку», только длиннее.
- **Автоматизация** — движка правил в разделе нет и не планировалось. У стадий задач нет
  даже стабильного машинного ключа (в отличие от продлений) — он там существует именно ради
  авто-правил. Пункт из референса пропускаем осознанно.
- **Перетаскивание колонок мышью** — на доске уже висит `DndContext` для карточек, второй
  слой перетаскивания рядом с ним стоит дороже, чем даёт. Порядок меняют пункты меню.

## Задачи

### Задача 0: уравнять права админа и суперадмина

**Файлы:** `apps/taskboard/views.py`, тесты раздела,
`frontend/admin-src/src/lib/permissions.ts`

Заказчик решил: админ и суперадмин имеют одинаковые права и на воронки, и на стадии.

Подходящий класс УЖЕ существует — `ReadStaffWriteAdmin` в `apps/core/permissions.py`
(читают сотрудники, пишут admin и superadmin). Изобретать ничего не нужно: заменить им
`ReadStaffWriteSuperAdmin` в пяти вьюхах — `BoardCollectionView`, `BoardDetailView`,
`StageCollectionView`, `StageDetailView`, `StageReorderView`.

Тесты: там, где сейчас проверяется «менеджер не может» — оставить; добавить «админ может»
на создание, правку и удаление и воронки, и стадии. Существующие проверки суперадмина
обязаны остаться зелёными.

На фронте `canWriteTaskStages` становится `isAdminUp`. Отдельный предикат для воронок
НЕ заводим — права одинаковые, вторая сущность только запутает.

### Задача 0b: reorder переезжает под воронку и перестаёт падать

**Файлы:** `apps/taskboard/urls.py`, `apps/taskboard/views.py`,
`apps/taskboard/serializers.py`, тесты, фронтовый вызов

Сейчас `POST /api/admin/tasks/stages/reorder` не принимает воронку, а **выводит** её из
присланных стадий: `boards = {s.board_id …}` → `boards.pop()`. На пустом `order` множество
пусто, и `pop()` кидает `KeyError` — эндпоинт отвечает **500 вместо 400**. Проверено на живом
эндпоинте 2026-08-27.

Лечим причину, а не симптом: маршрут становится
`POST /api/admin/tasks/boards/<board_id>/stages/reorder`. Воронка приходит явно, выводить
нечего, а пустой массив естественно упирается в существующую проверку полноты набора
(`incomplete_stage_set`). Заодно маршрут становится симметричен созданию стадии, которое
уже вложено в воронку.

Из вьюхи уходит вывод `board_id` и проверка `stages_from_different_boards` в прежнем виде:
теперь это «все присланные стадии обязаны принадлежать воронке из URL». Код ошибки оставить
прежним — он уже переведён в `TASK_CONFLICT_LABELS`, и менять его значит трогать подписи
без нужды.

Регрессионные тесты: пустой `order` → 400 (не 500); стадия чужой воронки в наборе → 400;
неполный набор → 400; нормальная перестановка → 200 и новый порядок.

`PATCH` и `DELETE /stages/<pk>` остаются плоскими: id стадии глобально уникален, вложение
не добавило бы ни адресации, ни защиты — права проверяются по роли, а не по воронке.

### Задача 1: мутации стадий на доске

**Файл:** `hooks/useTaskStructure.ts`

Добавить `useStageMutations()` с `create` / `update` / `remove` / `reorder` по образцу
уже существующего `useBoardMutations()`.

**Критично — что сбрасывать.** Ключи раздела намеренно разведены: `['tasks','ref',…]` —
справочники, `['tasks','cards',…]` — карточки И счётчики колонок. Стадия относится к обоим:
её правка меняет и справочник стадий, и набор колонок доски (`column_counts` живёт под
`cards`). Поэтому мутации стадий обязаны сбрасывать **оба** ключа — иначе переименованная
колонка останется со старым названием до перезагрузки страницы.

**Тонкость `reorder`:** бэкенд требует ПОЛНЫЙ набор id стадий воронки в поле `order`, иначе
отвечает `incomplete_stage_set`. Сдвиг на шаг — это перестановка двух соседей в полном
массиве и отправка его целиком.

### Задача 2: меню в шапке колонки

**Файлы:** `pages/tasks/TaskColumn.tsx`, `pages/tasks/StageSettingsDialog.tsx` (создать),
`styles/pages/tasks.css`

Меню собирается в `TaskColumn` и уходит в `actions` компонента `BoardColumnHead`.
Кнопки меню на цветной плашке наследуют её цвет — правило `.board-col-head__actions` это
уже задаёт.

Ошибки показывать через `useApiError()` + `conflictError`, тосты — по образцу переноса
карточки.

### Задача 3: плитка «Добавить колонку»

**Файлы:** `pages/tasks/TaskBoard.tsx`, `styles/pages/tasks.css`

Плитка рендерится после всех колонок, шириной с колонку, приглушённая.

### Задача 4: проверка

- `npm run typecheck`;
- полный `pytest` — бэкенд не менялся, но прогон подтверждает, что ничего не задето;
- ручной прогон: переименование, цвет, смена вида стадии, сдвиги, удаление, добавление.
  Отдельно проверить отказы: удаление стадии с задачами и удаление последней открытой
  (или последней закрытой) стадии обязаны давать понятное сообщение, а не молчание.

## Принятые решения

### Права

**Админ и суперадмин уравнены и по воронкам, и по стадиям** (решение заказчика, 2026-08-27).
Реализация — Задача 0.

Менеджер стадии и воронки не правит: он ведёт задачи внутри готовой структуры, а структура
общая для всей школы — удалённая стадия ломает доску сразу всем.

### Судьба страницы `/admin/tasks/stages`

Рекомендация: **оставить в этой итерации**. Она управляет ещё и воронками (архивирование,
переименование, порядок), а стадии там будут дублировать доску. Убирать дубль — отдельная
уборка, и держать запасной путь, пока новый способ обкатывается, разумнее.
